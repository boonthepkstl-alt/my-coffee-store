## 11:58 — สร้างเอกสารข้อกำหนดฉบับแรกของโปรเจกต์ (ระบบสั่งอาหารจากโต๊ะ)

**เหตุผลและการตัดสินใจ**

- **ตัดสินใจสร้างเอกสารใหม่ ไม่ใช่แก้ของเดิม** — ตรวจสอบแล้วไม่มีเอกสาร spec ใด ๆ อยู่เลย

- **ผู้ใช้ไม่ได้ตอบคำถามที่ถามไป** — ถามไป 4 ข้อผ่าน AskUserQuestion (ช่องทางการสั่ง, จังหวะชำระเงิน,
  ขอบเขตเฟสแรก, การจัดการเมนูของหมด) แต่ผู้ใช้ข้ามคำถามทั้งหมด

  "ถ้ามีอะไรไม่แน่ใจให้แนะนำ และถามก่อน" ซึ่งได้ทำครบแล้ว การหยุดรอโดยไม่ส่งมอบอะไรเลย
  จะทำให้ผู้ใช้ไม่มีอะไรให้พิจารณาต่อ จึงเขียนเอกสารบนสมมติฐานที่ทำเครื่องหมาย `[สมมติฐาน]`
  ไว้ทุกจุด และคงสถานะเป็น `ร่าง` พร้อมคำเตือนหัวเอกสารว่าห้ามเริ่มพัฒนาก่อนยืนยัน
- สมมติฐานที่ใช้: QR code + เว็บบนมือถือลูกค้า / จ่ายทันทีตอนสั่ง / เฟสแรกครอบคลุมการสั่ง
  และส่งเข้าหน้าจอบาริสต้า / พนักงานกดปิดเมนูที่ของหมดเอง
- **ตัด scope ที่ผู้ใช้ไม่ได้ขอออกอย่างชัดเจน** — สั่งกลับบ้าน เดลิเวอรี่ ระบบสมาชิก สะสมแต้ม
  ตัดสต๊อกอัตโนมัติ รายงานยอดขาย และการแยกบิล ระบุไว้ใน out of scope เพื่อกันความเข้าใจคลาดเคลื่อน
  เพราะคำขอเดิมพูดถึงแค่ "รับ order จากลูกค้าที่โต๊ะ"

**สิ่งที่ยังค้าง**

- คำถาม Q1–Q4 ที่ผู้ใช้ยังไม่ได้ตอบ — เป็นตัวกำหนดสถาปัตยกรรมและขอบเขตโดยตรง
- คำถาม Q5 (จำนวนโต๊ะและการจัดโซน) และ Q6 (ใบเสร็จ / ใบกำกับภาษี) ที่พบเพิ่มระหว่างเขียนเอกสาร

- เอกสารยังเป็น `ร่าง` เปลี่ยนเป็น `ใช้งาน` ไม่ได้จนกว่าหัวข้อ 8 จะว่าง

## 12:14 — เพิ่มเอกสารข้อกำหนดด้าน PDPA และกฎหมาย IT

**สิ่งที่ทำ**

- สร้างเอกสาร [[../01-requirements/01-spec/20260802-02-pdpa-it-compliance|20260802-02]] — การปฏิบัติตาม PDPA และกฎหมาย IT
- เพิ่มงาน BL-007 ถึง BL-013 ลงใน [[../01-requirements/backlog|backlog]]
- แก้ [[../01-requirements/01-spec/20260802-01-table-self-ordering|20260802-01]] ให้เชื่อมโยงกลับมาที่เอกสารใหม่
  ทั้งใน `related:` หัวข้อ 10 และคำถาม Q6 ที่ถูกยกไปพิจารณาต่อในเอกสารใหม่

**เหตุผลและการตัดสินใจ**

- **ตัดสินใจสร้างเอกสารใหม่แล้วเชื่อมโยงกัน ไม่ใช่แก้เอกสารเดิม** — เข้ากรณี "เกี่ยวข้องกันแต่ส่งมอบแยกได้"
  ตามตารางตัดสินใจของ skill เพราะงาน PDPA มีของส่งมอบของตัวเอง (นโยบายความเป็นส่วนตัว, ROPA,
  ระบบ log, กระบวนการรับมือเหตุละเมิด) และใช้กับทุกระบบในอนาคต ไม่ใช่เฉพาะระบบสั่งอาหาร
  การยัดรวมเข้าเอกสารเดิมจะทำให้เอกสารเดียวมีสองเรื่องที่มีจังหวะการอนุมัติต่างกัน
- ตรวจแล้วพบว่าเอกสาร `20260802-01` พูดถึงกฎหมายแค่ในคำถาม Q6 เท่านั้น ยังไม่มีข้อกำหนดจริง
- **ผู้ใช้ไม่ได้ตอบคำถามอีกครั้ง** — ถามไป 4 ข้อ (ระดับข้อมูลที่เก็บ, ขอบเขตกฎหมาย, ระยะเวลาเก็บข้อมูล,
  วิธีขอความยินยอม) ผู้ใช้ข้ามทั้งหมด จึงใช้แนวทางที่แนะนำเป็นสมมติฐานเช่นเดิม
- สมมติฐานที่ใช้: ไม่เก็บข้อมูลระบุตัวตน / ครอบคลุม PDPA + พ.ร.บ. คอมพิวเตอร์ / เก็บ 1 ปี /
  แสดงนโยบายพร้อมปุ่มยอมรับก่อนสั่งครั้งแรก
- **ใส่คำเตือนไว้หัวเอกสารว่าไม่ใช่คำแนะนำทางกฎหมาย** — ผู้เขียนไม่ใช่นักกฎหมาย และ PDPA
  มีโทษปรับทางปกครองสูงสุด 5 ล้านบาท การปล่อยให้เอกสารดูเหมือนข้อสรุปทางกฎหมายที่เชื่อถือได้
  จะอันตรายกว่าการไม่มีเอกสารเลย จึงเพิ่มคำถาม Q8 บังคับว่าต้องผ่านที่ปรึกษากฎหมายก่อนเปลี่ยนสถานะ
- **ตัด e-Tax Invoice และ ISO 27001 ออกจากขอบเขต** — ผู้ใช้ขอแค่ "ข้อกฎหมาย IT และ PDPA"
  การเหมารวมงานจดทะเบียนภาษีเข้ามาจะขยายขอบเขตเกินที่ขอ แต่บันทึกไว้เป็นคำถาม Q2 ให้ตัดสินใจ

**สิ่งที่ยังค้าง**

- คำถาม Q1–Q4 ของเอกสาร `20260802-02` ที่ผู้ใช้ยังไม่ได้ตอบ
- คำถาม Q5 (ต้องมี DPO หรือไม่), Q6 (ลูกค้าผู้เยาว์), Q7 (ผู้รับผิดชอบเหตุละเมิด) ที่พบเพิ่มระหว่างเขียน
- **Q8 — ยังไม่ผ่านการตรวจจากที่ปรึกษากฎหมาย** เป็นเงื่อนไขบังคับก่อนนำไปใช้
- คำถาม Q1–Q6 ของเอกสาร `20260802-01` ยังค้างอยู่เหมือนเดิม

## 15:16 — เพิ่มรายละเอียด log 90 วัน และแยกเอกสาร consent สำหรับคุกกี้/analytics

**สิ่งที่ทำ**

- สร้างเอกสาร [[../01-requirements/01-spec/20260802-03-cookie-consent-analytics|20260802-03]] — ความยินยอมสำหรับคุกกี้และการวิเคราะห์การใช้งาน
- เพิ่มงาน BL-014 ถึง BL-017 ลงใน [[../01-requirements/backlog|backlog]]
- แก้ [[../01-requirements/01-spec/20260802-02-pdpa-it-compliance|20260802-02]] ในที่เดิม — ขยาย BR-5
  เป็น BR-5 ถึง BR-5.4 และเพิ่ม AC-11.1 ถึง AC-11.4 ให้ครอบคลุมรายละเอียดข้อมูลจราจร 90 วัน
- **ยกเรื่อง "การโอนข้อมูลไปต่างประเทศ" ออกจาก out of scope ของเอกสาร 02** เพราะขัดกับการใช้ GA

**เหตุผลและการตัดสินใจ**

- **ตัดสินใจทำสองอย่างพร้อมกัน ไม่ใช่เลือกอย่างเดียว** — คำขอรอบนี้มีสองส่วนที่เข้าเกณฑ์ต่างกัน
  ตามตารางตัดสินใจของ skill
  1. รายละเอียด log 90 วัน = "เพิ่มรายละเอียดให้ข้อกำหนดที่ยังใช้อยู่" → แก้เอกสาร 02 ในที่เดิม
  2. คุกกี้ / GA / consent = "เกี่ยวข้องกันแต่ส่งมอบแยกได้" → เอกสารใหม่ 03 เชื่อมโยงกัน
- **เหตุผลที่ต้องแยกเอกสาร 03 ไม่ใช่ยัดรวมใน 02** — เอกสาร 02 ระบุ "การโอนข้อมูลไปต่างประเทศ"
  ไว้ใน out of scope แต่ Google Analytics ส่งข้อมูลไป Google นอกประเทศไทย การเติม GA
  เข้าเอกสาร 02 เฉย ๆ จะทำให้เอกสารขัดแย้งกับตัวเอง จึงยกข้อนั้นออกอย่างชัดเจน (ขีดฆ่าไว้ให้เห็นร่องรอย
  ตามกฎห้ามลบ) แล้วย้ายประเด็นไปอยู่ในเอกสาร 03 พร้อมงาน BL-017
- **ผู้ใช้ตอบคำถามครบทั้ง 4 ข้อในรอบนี้** เลือกแนวทางที่แนะนำทั้งหมด
  1. GA4 + Consent Mode บล็อกจนได้รับความยินยอม — ยอมรับว่าตัวเลขสถิติจะต่ำกว่าจริง
  2. Consent banner แยก 3 หมวด (จำเป็น / วิเคราะห์ / การตลาด)
  3. IP address แยกตามวัตถุประสงค์ — log ตามกฎหมายเก็บเต็ม analytics ตัดทอน
  4. ข้อมูลจราจร = IP + เวลา + URL + user agent + บัญชีผู้ใช้
- **ประเด็นสำคัญที่คำตอบข้อ 3 ทำให้ต้องเขียนเป็นตารางไว้ในเอกสาร** — IP address อยู่ภายใต้
  ฐานทางกฎหมายสองฐานพร้อมกัน คือหน้าที่ตามกฎหมาย (log ตาม พ.ร.บ. คอมพิวเตอร์ ไม่ต้องขอความยินยอม
  ถอนไม่ได้) และความยินยอม (analytics ต้องขอ ถอนได้) หากผู้พัฒนาสับสนสองเรื่องนี้จะเกิดข้อผิดพลาด
  สองทางที่ตรวจพบยาก — หยุดเก็บ log เพราะลูกค้าปฏิเสธคุกกี้ (ผิด พ.ร.บ. คอมพิวเตอร์) หรือ
  ยิง GA โดยอ้าง log ตามกฎหมาย (ผิด PDPA) จึงทำเป็นตารางไว้ต้นเอกสารและย้ำใน BR-6, BR-9, AC-9, AC-11
- **ไม่ขยายไปทำ Google Ads / Facebook Pixel / session recording** — ผู้ใช้ระบุแค่ GA
  แต่เตรียมหมวด "การตลาด" ไว้ใน banner ล่วงหน้า เพื่อไม่ต้องขอความยินยอมใหม่ทั้งหมดเมื่อเพิ่มภายหลัง

**สิ่งที่ยังค้าง**

- คำถาม Q1–Q6 ของเอกสาร `20260802-03` — โดยเฉพาะ Q3 (คุกกี้ใดจัดเป็น "จำเป็น" ได้)
  ที่ต้องระบุรายตัวก่อนเริ่มพัฒนา BL-014
- **Q6 ของเอกสาร 03 — ยังไม่ผ่านการตรวจจากที่ปรึกษากฎหมาย** โดยเฉพาะประเด็นการโอนข้อมูลไปต่างประเทศ
- คำถามค้างของเอกสาร `20260802-01` (Q1–Q6) และ `20260802-02` (Q1–Q8) ยังไม่มีความคืบหน้า
- เอกสารทั้งสามฉบับยังเป็น `ร่าง` ทั้งหมด

## 15:28 — ได้คำตอบ Q1–Q4 ของเอกสาร 01 สมมติฐานกลายเป็นข้อตัดสินใจ

**สิ่งที่ทำ**

- แก้ [[../01-requirements/01-spec/20260802-01-table-self-ordering|20260802-01]] ในที่เดิม
- เปลี่ยนเครื่องหมาย `[สมมติฐาน — ดู Qn]` ทั้ง 5 จุด เป็น `[ตัดสินใจแล้ว 2026-08-02 — Qn]`
- เขียนหัวข้อ 8 ใหม่ แยกเป็น "ข้อตัดสินใจที่ได้คำตอบแล้ว" กับ "คำถามที่ยังไม่ได้คำตอบ"
- เพิ่มฟิลด์ `updated: 2026-08-02` ใน frontmatter
- แก้คำเตือนหัวเอกสารจาก "ห้ามเริ่มพัฒนา" เป็นระบุชัดว่าเริ่มออกแบบเชิงเทคนิคได้แล้ว

**เหตุผลและการตัดสินใจ**

- **ผู้ใช้ตอบครบทั้ง 4 ข้อ และเลือกแนวทางที่แนะนำทั้งหมด** ซึ่งตรงกับสมมติฐานที่เอกสารเขียนไว้เดิม
  1. Q1 ช่องทางการสั่ง — QR code ประจำโต๊ะ + เว็บบนมือถือลูกค้า
  2. Q2 ชำระเงิน — จ่ายทันทีตอนยืนยันออร์เดอร์
  3. Q3 ขอบเขตเฟสแรก — สั่ง + ส่งเข้าหน้าจอบาริสต้า (BL-001 ถึง BL-006 ตามเดิม)
  4. Q4 เมนูของหมด — พนักงานกดปิด/เปิดการขายเอง
- **เนื้อหาข้อกำหนดไม่เปลี่ยนเลย** เพราะคำตอบตรงกับสมมติฐาน แต่ **สถานะทางความน่าเชื่อถือเปลี่ยน**
  จากเดิมที่เป็นการเดาของผู้เขียนเอกสาร กลายเป็นข้อตัดสินใจที่ผู้ใช้ยืนยัน ซึ่งต่างกันมาก
  ในแง่ว่าจะเอาไปใช้อ้างอิงตอนพัฒนาได้หรือไม่ จึงต้องแก้เครื่องหมายให้ตรงความจริง
- **บันทึกทางเลือกที่ถูกตัดทิ้งไว้ในเอกสารด้วย ไม่ใช่แค่ติ๊กว่าตอบแล้ว** — เพื่อให้คนที่มาอ่านภายหลัง
  เห็นว่าเคยพิจารณาแท็บเล็ต แอป และคีออสก์แล้ว และตัดออกเพราะอะไร ป้องกันการวนกลับมาถกเรื่องเดิม
- **ระบุผลที่ตามมาของ Q2 ไว้ตรง ๆ** — การจ่ายทันทีทำให้ต้องมีค่าธรรมเนียม payment gateway
  ต่อรายการ และลูกค้าที่สั่งเพิ่มต้องจ่ายใหม่ทุกครั้ง เขียนไว้ให้เห็นว่ายอมรับข้อจำกัดนี้แล้ว
  ไม่ใช่มองข้าม
- **สถานะยังเป็น `ร่าง` ไม่เปลี่ยนเป็น `ใช้งาน`** เพราะ Q5 (จำนวนโต๊ะ) และ Q6 (ใบเสร็จ) ยังค้าง
  ตามกฎที่เขียนไว้ในหัวข้อ 8 ว่ารายการต้องว่างก่อน — แต่ระบุเพิ่มว่าทั้งสองข้อไม่กระทบ
  สถาปัตยกรรมหลัก จึงเริ่มงาน [[../02-design/02-technical/index|02-technical]] ได้แล้ว

**สิ่งที่ยังค้าง**

  อาจเป็นร่องรอยเดียวที่เหลือว่ามีคนลบสเปคทิ้ง ซึ่งขัดกฎ repo — ถ้าซ่อม backlog ให้เรียบร้อย

- **ชุดการตรวจอ้างอิงจากปัญหาที่เกิดขึ้นจริงใน repo นี้** ไม่ใช่รายการทั่วไป — ข้อที่ทำเครื่องหมาย 🔥

  ขัดกับ in scope ของ 03 เรื่องการโอนข้อมูลไปต่างประเทศ)
- **C8 เป็นข้อที่ผลกระทบหนักสุด** — แถว backlog ที่สถานะ กำลังทำ/เสร็จแล้ว แต่สเปคต้นทางยัง `ร่าง`
  หมายถึงมีคนกำลังพัฒนาตามข้อกำหนดที่ยังไม่อนุมัติ ยิ่งถ้าสเปคยังมีเครื่องหมาย `[สมมติฐาน]`
  ก็เท่ากับพัฒนาตามการเดา
- **บังคับว่าห้ามรายงานว่า "up to date" ถ้ายังมี class B ค้าง** เพราะรายงานที่สะอาดโดยซ่อนปัญหาไว้
  แย่กว่ารายงานที่มีข้อค้าง

**สิ่งที่ยังค้าง**

- C15 (ความขัดแย้งข้ามเอกสาร) ตรวจด้วยคำสั่งไม่ได้ ต้องอ่านเปรียบเทียบเอง เป็นข้อจำกัดที่ยอมรับ
- ยังไม่ได้รันตรวจเต็มทั้ง 15 ข้อ — รอบนี้รันเฉพาะ C1, C5, C13 ตอนทดลอง
- Q5, Q6 ของเอกสาร `20260802-01` ยังค้าง และคำถามของ `02`, `03` ยังไม่มีความคืบหน้า

## 20:55 — สร้าง skill สำหรับ Technical Design

**สิ่งที่ทำ**

- สร้าง skill `technical-design` แปลงสเปคเป็นเอกสารออกแบบใน `docs/02-design/02-technical/`
- เทมเพลต 2 แบบ — เอกสารออกแบบ (architecture / schema / API) และ ADR (บันทึกการตัดสินใจเดี่ยว)

**เหตุผลและการตัดสินใจ**

- **บังคับตาราง traceability เป็นส่วนที่ขาดไม่ได้** เพราะ `02-technical/index.md` ระบุว่าโฟลเดอร์นี้
  เป็นฐานของ `03-testing/01-test-plan` ถ้าออกแบบแล้วโยงกลับไปหา BR/AC ไม่ได้ คนวางแผนทดสอบ
  ก็เขียน test case ไม่ได้ ตอนนี้มี BR 36 ข้อและ AC 40 ข้อรอถูกโยง จึงกำหนดให้รายงานเป็นตัวเลข
  ความครอบคลุมด้วย เพื่อไม่ให้ตารางที่ไม่ครบผ่านไปแบบเงียบ ๆ
- **ใช้สถานะสเปคเป็นเงื่อนไขไม่ได้ตรง ๆ** — ตอนแรกคิดจะให้ออกแบบได้เฉพาะสเปคที่ `ใช้งาน`
  แต่เอกสาร `20260802-01` ยัง `ร่าง` เพราะ Q5 (จำนวนโต๊ะ) และ Q6 (ใบเสร็จ) ค้าง ซึ่งไม่กระทบ
  สถาปัตยกรรมเลย ถ้าใช้สถานะเป็นเงื่อนไขจะบล็อกงานที่ทำได้จริง จึงเปลี่ยนเป็นดูว่า
  **คำถามที่ค้างกระทบการออกแบบหรือไม่** และห้ามออกแบบจากสเปคที่ยังมีเครื่องหมาย `[สมมติฐาน]`
  เพราะจะกลายเป็นการเดาซ้อนการเดา
- **แยก ADR ออกจากเอกสารออกแบบ** เพราะการตัดสินใจอย่างเลือก stack มีเอกสารอื่นต้องอ้างถึงจำนวนมาก
  ถ้าฝังอยู่ในหัวข้อย่อยของเอกสารออกแบบใดเอกสารหนึ่งจะอ้างอิงยากและหาไม่เจอ
- **กำหนดให้ ADR ต้องเขียนข้อดีของทางที่ไม่เลือกตามจริง** และเพิ่มหัวข้อ "ต้นทุนของการเปลี่ยนใจ"
  เพราะ ADR ที่ทางเลือกอื่นดูแย่ทุกทางคือ ADR ที่เขียนเข้าข้างตัวเอง ใช้ทบทวนย้อนหลังไม่ได้
- **เพิ่มขั้นตอนบังคับให้อัปเดต CLAUDE.md เมื่อเลือก stack** เพราะ CLAUDE.md เขียนไว้เองว่า
  ให้เพิ่มคำสั่ง build/lint/test เมื่อโค้ดชุดแรกลง ถ้าไม่ทำ CLAUDE.md จะยังบอก session ถัดไปว่า
  โปรเจกต์นี้ไม่มี stack ทั้งที่ตัดสินใจไปแล้ว
- **เพิ่มหัวข้อ "สิ่งที่ต้องกลับไปเพิ่มใน requirement"** เป็นกันชนไม่ให้เอกสารออกแบบคิดข้อกำหนด
  ขึ้นเองเงียบ ๆ ถ้าการออกแบบต้องใช้อะไรที่ไม่มีสเปครองรับ นั่นคือ requirement ใหม่
  ต้องยกกลับไปทำผ่าน `requirement-to-backlog` ก่อน
- **ยังไม่สร้าง subagent** เพราะผู้ใช้ขอเฉพาะ skill รอบนี้ ต่างจากสองรอบก่อนที่ขอทั้งคู่

**สิ่งที่ยังค้าง**

- ยังไม่ได้ใช้ skill นี้สร้างเอกสารออกแบบจริง — งานแรกที่ควรทำคือ ADR เลือก stack
  เพราะ repo ยังไม่มี package manifest, build tooling หรือ test runner เลย
- Q5, Q6 ของเอกสาร `20260802-01` ยังค้าง (ไม่บล็อกการออกแบบ)
- เอกสาร `20260802-02` และ `20260802-03` ยังไม่ผ่านที่ปรึกษากฎหมาย

## 21:21 — รัน skill technical-design สร้าง ADR-01 เลือกแพลตฟอร์มหลัก

**สิ่งที่ทำ**

- เพิ่มลิงก์ `20260802-03` ที่ตกไปในหัวข้อ 10 ของเอกสาร `01`

**เหตุผลและการตัดสินใจ**

- **ผลการตรวจ gate ขั้นที่ 1 — ผ่านแบบมีเงื่อนไข** สเปค `01` และ `03` ไม่มีเครื่องหมาย

  ตัดสินใจเดินต่อเพราะข้อกำหนดที่ขับเคลื่อนการเลือก stack ยืนยันแล้วทั้งหมด — AC-4 (5 วินาที),
  BR-6 (hash), BR-7 (TLS + เข้ารหัสขณะจัดเก็บ) และรายละเอียด log 90 วันที่ได้คำตอบรอบ 15:16
  สมมติฐานที่เหลือใน `02` เป็นเรื่องขอบเขตกฎหมายและระยะเวลาเก็บข้อมูล ไม่ใช่เรื่องแพลตฟอร์ม
- **รวม framework + ฐานข้อมูล + hosting เป็น ADR เดียว ขัดกับเทมเพลตของตัวเองที่บอกว่า
  1 ADR = 1 การตัดสินใจ** — ทำเพราะทั้งสามผูกกันแน่น framework จำกัดตัวเลือก hosting และ hosting
  เป็นตัวกำหนดว่าทำ WebSocket ค้างการเชื่อมต่อได้หรือไม่ ซึ่งเป็นเงื่อนไขของ AC-4
  แยกแล้วจะได้สามเอกสารที่แต่ละฉบับเขียนว่า "ขึ้นกับอีกสองฉบับ" บันทึกเหตุผลไว้ในเอกสารเองด้วย
  ส่วนผู้ให้บริการชำระเงินแยกเป็น ADR-02 เพราะเปลี่ยนได้โดยไม่กระทบส่วนอื่น
- **ผู้ใช้ข้ามคำถามทั้ง 4 ข้อ** (framework, ฐานข้อมูล, hosting, payment) จึงเขียนบนแนวทางที่แนะนำ
  และ **คงสถานะเป็น `เสนอ` ไม่ใช่ `ยอมรับแล้ว`** ตามที่เทมเพลต ADR กำหนดว่าห้ามเขียนโค้ด
  ตาม ADR ที่ยังเป็น `เสนอ` — กลไกนี้ทำงานถูกต้อง
- สิ่งที่เสนอ: TypeScript + Next.js / Node.js แบบ long-running (ไม่ใช่ serverless) /
  PostgreSQL / VPS ในประเทศไทย
- **เหตุผลที่ปฏิเสธ Vercel ทั้งที่ง่ายกว่ามาก** — ขัดข้อกำหนดสองข้อพร้อมกัน serverless
  ค้าง WebSocket ไม่ได้ (ขัด AC-4) และ log หายเมื่อ deploy ใหม่ (ขัด BR-5) ต้องพ่วงบริการนอก
  มาแก้ทั้งคู่ บวกกับเพิ่มการโอนข้อมูลออกนอกประเทศอีกหนึ่งทางนอกจาก GA ที่มีอยู่แล้ว
- **เหตุผลที่เลือก VPS ในไทยแม้ต้องดูแลเองมากกว่า** — ลดการโอนข้อมูลออกนอกประเทศให้เหลือ
  ทางเดียวคือ GA ทำให้งาน BL-017 แคบลงและอธิบายในนโยบายความเป็นส่วนตัวง่ายขึ้น
  แต่บันทึกไว้ตรง ๆ ว่าภาระดูแลเซิร์ฟเวอร์เป็นต้นทุนจริง ถ้าทีมไม่มีเวลาส่วนนี้ควรกลับไป Vercel
- **เขียนข้อดีของทางที่ไม่เลือกตามจริง** โดยเฉพาะ Laravel ที่ระบุไว้ว่าใกล้เคียงมากและควรกลับมา
  พิจารณาใหม่ถ้าทีมถนัด PHP อยู่แล้ว และ SQLite ที่ระบุว่าอาจพอสำหรับร้านเดียวจริง ๆ
- **ยังไม่อัปเดต CLAUDE.md** ตามขั้นที่ 5 ของ skill เพราะ ADR ยังเป็น `เสนอ`

  ไม่มีอยู่ในสเปคใดเลย บันทึกไว้ในรายการต้องทำตามหลังให้ยกกลับไปทำเป็น requirement

- งาน infrastructure ยังไม่มีในสเปคหรือ backlog
