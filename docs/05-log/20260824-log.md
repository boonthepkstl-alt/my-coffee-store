  ออกแบบ แทนการหยุดทำทั้งเอกสาร เพราะส่วนใหญ่ของงาน (สเปค `01`, `03`) ไม่ติดปัญหา
  เดียวกัน
- **ถามผู้ใช้ 2 เรื่องก่อนเขียน** ตามขั้นที่ 2 ของ skill (เทคโนโลยีที่สเปคบังคับ
  แต่ยังไม่ตัดสินใจ) — ผู้ใช้ตอบทั้งสองข้อ:
  1. Payment gateway — เลือกแนวทางที่แนะนำ (PromptPay QR ผ่าน gateway ไทย)
  2. Image storage (รูปเมนู) — เลือก **Object storage แบบ S3-compatible**
     ซึ่ง**ไม่ใช่**ตัวเลือกที่แนะนำ (ที่แนะนำคือเก็บบน VPS เดียวกับแอปเพื่อลดความ
     ซับซ้อน) — บันทึกไว้ตรง ๆ ว่าเป็นตัวเลือกที่ผู้ใช้เลือกเอง ไม่ปัดเป็นการยืนยัน
     คำแนะนำ
- **แยก ADR-02 (payment) เป็นเอกสารเดี่ยว แต่ไม่แยก ADR สำหรับ image storage** —
  payment กระทบหลายเอกสาร (BL-004, AC-4, AC-5, schema ตาราง payments) และมี
  ผลทางพาณิชย์ที่คนอื่นต้องอ้างถึงได้ ตรงกับเกณฑ์ "decision ที่เอกสารอื่นต้องอ้างถึง"
  ของ skill ส่วน image storage กระทบแค่คอลัมน์เดียว (`menu_items.photo_url`)
  และไม่มีผลทางกฎหมาย/พาณิชย์เท่าเทียมกัน จึงเขียนไว้ในตาราง §3 ของเอกสารออกแบบ
  พอ ไม่ต้องแยกไฟล์
- **ADR-02 ตัดสินใจแค่ "รูปแบบ" (PromptPay QR + webhook) ไม่ใช่ชื่อบริษัทจริง** —
  การเลือกผู้ให้บริการรายจริง (Omise/2C2P/GB Prime Pay) เป็นการตัดสินใจเชิง
  พาณิชย์ (ค่าธรรมเนียม สัญญา) ที่ควรทำตอนเริ่มพัฒนาจริง ไม่ใช่ตอนออกแบบ
  สถาปัตยกรรม — แยกสองเรื่องนี้ออกจากกันชัดเจนเพื่อไม่ให้ ADR ต้องรอการเจรจา
  สัญญาที่ยังไม่เกิดขึ้น
- **เลือก Argon2id สำหรับ password hashing โดยไม่ต้องถามผู้ใช้** — ต่างจาก
  payment/storage ที่มีผลทางพาณิชย์หรือทางเลือกทางธุรกิจ การเลือกอัลกอริทึม
  hash รหัสผ่านเป็นค่าเริ่มต้นทางเทคนิคที่มีมาตรฐานชัดเจน (แนะนำเหนือ bcrypt
  สำหรับระบบใหม่) ไม่จำเป็นต้องรอการตัดสินใจทางธุรกิจ
- **`order_items` เก็บ snapshot ชื่อ/ราคา แยกจาก `menu_items`** — เป็นกลไกเดียว
  ที่ทำให้ BR-4/AC-9 ของสเปค `01` (แก้ราคาใหม่ไม่กระทบออร์เดอร์เดิม) เป็นจริงได้
  ในระดับ schema ถ้าอ้างอิง `menu_items` ตรง ๆ ไม่เก็บ snapshot ราคาที่แก้ไปแล้ว
  จะกระทบย้อนหลังทันที
- **`traffic_logs` แยกสิทธิ์ DB role ไม่ให้ UPDATE/DELETE** ไม่ใช่แค่ "ตกลงกันว่า
  จะไม่แก้" — เพราะ BR-5.2/AC-11.3 ของสเปค `02` ต้องการว่า "แก้ไขย้อนหลังไม่ได้"
  ซึ่งเป็นคุณสมบัติที่ต้องบังคับที่ระดับฐานข้อมูล ไม่ใช่แค่ข้อตกลงในทีม
- **แก้ปัญหา reconnect ของ BL-005 ที่ทิ้งไว้เป็นคำถามค้างตั้งแต่ 2026-08-19** —
  ออกแบบ `GET /orders?status=confirmed&since=` ให้ client ดึงข้อมูลค้างมาแสดง
  ครบตอนเชื่อมต่อ WebSocket กลับ แทนการรอ event ถัดไปเฉย ๆ — เป็นคำตอบทางเทคนิค
  ให้กับคำถามที่ journey ทิ้งไว้ ไม่ใช่คำถามใหม่
- **พบช่องว่างจริงระหว่างออกแบบ: AC-10 ของสเปค `02` ต้องการ log การเข้าถึงที่
  สำเร็จด้วย ไม่ใช่แค่ที่ถูกปฏิเสธ** — เอกสารออกแบบมีแค่ `access_denials`
  (บันทึกเฉพาะกรณีถูกปฏิเสธ) ไม่ได้เดาเติม schema สำหรับ "access ที่สำเร็จ" ขึ้นมา
  เอง เพราะขอบเขตที่แท้จริงของ audit log (บันทึกทุกครั้งที่มีคนเห็นข้อมูลอะไร
  หรือเฉพาะกรณีผิดปกติ) เป็นคำถามที่ควรกลับไปยืนยันกับ requirement ก่อน ไม่ใช่
  รายละเอียดการออกแบบที่ควรเดาเอง
- **ตีความ AC-2 ของสเปค `01`** ว่าหมายถึง endpoint สาธารณะ (`GET /menu`) แยกจาก
  มุมมองพนักงาน (`GET /menu/items`) เพื่อให้ออกแบบ API ต่อได้ — บันทึกไว้ชัดว่า

  บันทึกไว้ตั้งแต่ทำ test case ของ BL-001 แล้ว) ควรยืนยันจริงตอนทำ BL-003

## 14:10 — เขียน ADR-03: แก้ไข backend จาก Next.js/Node.js รวมเป็น Go แยกบริการ

**สิ่งที่ทำ**

ผู้ใช้สั่งเปลี่ยน stack: "frontend ใช้ react, next.js / backend ใช้ go / db ใช้
postgres / ส่วนที่เลือกช่วยเลือกให้เหมาะสมกับ project นี้" — ขัดกับ
