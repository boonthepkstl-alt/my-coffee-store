  ช่องว่างเดียวกันอีก
- **ไม่เพิ่ม state พิเศษสำหรับ "ออร์เดอร์กู้คืนมาช้า"** ที่หน้าจอบาริสต้า แม้ journey
  จะพูดถึงผลกระทบทางอ้อมไว้ — เพราะจากมุมมองของบาริสต้า ออร์เดอร์ที่กู้คืนสำเร็จ
  จะเข้าคิวเหมือนออร์เดอร์ปกติทุกประการ ไม่มีข้อกำหนดให้ต้องแยกแยะ การเพิ่ม state
  พิเศษโดยไม่มีหลักฐานจากสเปคจะเป็นการคิดฟีเจอร์ขึ้นเอง จึงไม่ทำ
- **Overall verdict คงเป็น NEEDS FIXES เหมือน pilot รอบแรก** ทั้งที่ WARNING น้อยกว่า
  (2 เทียบกับ 4) เพราะกฎของ `prototype-audit` ชัดเจนว่าห้ามปัดขึ้นเป็น PASS
  ทั้งที่มีอะไรค้าง ไม่ว่าจะค้างน้อยแค่ไหน

**สิ่งที่ยังค้าง**

- **Table vs Card** — ตอนนี้บล็อก 2 feature (BL-001, BL-005) ควรตัดสินใจก่อน
  ทำ feature ถัดไปที่มีรายการแบบเดียวกัน
- Reconnect/Resync pattern — ยังไม่มีใน DESIGN.md
- ลำดับการแสดงผลออร์เดอร์หลายใบในคิว, undo การกด "เสร็จแล้ว" ผิด — จาก journey §8
- คำถามค้างเดิมจาก BL-001 (Permission State, Switch/Checkbox, validation ราคา)
  ยังไม่มีความคืบหน้า

## 09:19 — ตัดสินใจ Table vs Card ใน DESIGN.md

**สิ่งที่ทำ**

- แก้ [[../../DESIGN.md|DESIGN.md]] §3 — เปลี่ยนจาก "ทั้งสองยังไม่ตัดสิน" เป็นกฎ
  ตัดสินใจตามรูปร่างข้อมูล พร้อมตารางเปรียบเทียบ
- เพิ่มแถวใน §7 Design Decisions พร้อมเหตุผล
- แก้เอกสาร prototype ทั้งสองฉบับที่เคยระบุว่า "ยังไม่ตัดสิน" ให้ตรงกับผลตัดสินใจ:
  - [[../02-design/01-prototypes/20260819-02-menu-management-prototype|BL-001 prototype]] → **Table**
  - [[../02-design/01-prototypes/20260819-04-barista-order-screen-prototype|BL-005 prototype]] → **Card**

**เหตุผลและการตัดสินใจ**

- **ไม่เลือกแบบเดียวตายตัวสำหรับทั้งสอง feature** แม้ผู้ใช้จะพูดว่า "ตัดสิน Table vs
  Card" แบบเอกพจน์ — เพราะข้อมูลจริงของสองหน้าจอมีรูปร่างต่างกันจริง: รายการเมนู
  เป็นแถวสม่ำเสมอ (ชื่อ/ราคา/สถานะ/ปุ่ม) เข้าเกณฑ์ Table ตามธรรมเนียม แต่คิว
  ออร์เดอร์แต่ละใบมีเนื้อหาหลายส่วนความยาวไม่เท่ากัน (โต๊ะ/รายการ/ตัวเลือก) และ
  ต้องอ่านได้เร็วภายใต้ความกดดันเวลา (ตรงกับ Visual Direction ที่ DESIGN.md §1
  อนุมานไว้แล้วจาก US-5) การบังคับใช้ Table กับคิวออร์เดอร์จะขัดกับความต้องการ
  จริงของหน้าจอนั้น จึงเขียนเป็น**กฎ**ตามรูปร่างข้อมูลแทนการเลือกค่าเดียว —
  ยังคงเป็นการตัดสินใจเดียวที่ใช้ได้ทั้งระบบ ไม่ใช่การเลี่ยงตัดสินใจ
- **เกณฑ์การแบ่งไม่ใช่ "ฝั่งลูกค้า vs ฝั่งพนักงาน"** เพราะทั้งสองตัวอย่างเป็นฝั่ง
  พนักงานเหมือนกัน — เขียนไว้ชัดในกฎเพื่อกันการเข้าใจผิดว่า Table=พนักงาน,
  Card=ลูกค้า ซึ่งไม่ตรงกับเหตุผลจริงที่ใช้ตัดสิน
- **ยกเลิกทั้งสอง WARNING ที่ prototype-audit เคยรายงานไว้ในสองรอบก่อน** (Table
  vs Card ของ BL-001 และ BL-005) — ทั้งคู่เข้าเกณฑ์ class A ตาม
  `requirement-backlog-audit` (spec/design ถูก คนแค่ยังไม่ตัดสินใจ) ตอนนี้มี
  คนตัดสินใจแล้วจึงซ่อมเอกสารที่เกี่ยวข้องได้ตรง ๆ ไม่ต้องรอ audit รอบใหม่

**สิ่งที่ยังค้าง**

- Permission State pattern, Switch vs Checkbox, validation ราคาเมนู (BL-001)
- Reconnect/Resync pattern, ลำดับคิวออร์เดอร์ (BL-005)
- ยังไม่ได้รัน prototype-audit ซ้ำเพื่อยืนยันว่า WARNING ของ Table/Card หายไปจริง
  ในรายงานเป็นทางการ (แก้เอกสารต้นทางแล้ว แต่รายงาน audit เดิมในบันทึกวันนี้ยัง
  เป็นภาพ ณ ตอนที่ยังไม่ตัดสินใจ — ไม่ได้ย้อนไปแก้ log เก่าตามกฎห้ามแก้ log ย้อนหลัง)
