# ADR-03 — แก้ไขแพลตฟอร์มหลัก: แยก backend เป็น Go, Next.js เหลือเฉพาะ frontend

> ✅ **สถานะ `ยอมรับแล้ว` (2026-08-24)** — ผู้ใช้ระบุ stack ตรง ๆ (frontend
> React/Next.js, backend Go, database Postgres) และขอให้เลือกส่วนที่เหลือให้
> เหมาะสม
>
> **เอกสารนี้ทดแทน [[../../00-archived/20260802-01-adr-platform-stack|ADR-01]]
> ตาม never-delete ของ repo (ย้ายไปเก็บที่ `00-archived/` ไม่ลบทิ้ง)** —
> เหตุผลที่ต้องเป็น ADR ใหม่ ไม่ใช่แก้ ADR-01 ในที่เดิม ดู "บริบท" ด้านล่าง

## บริบท

ADR-01 (2026-08-02) เลือก Next.js เป็นทั้ง frontend และ backend ในโค้ดชุดเดียว
โดยให้เหตุผลชัดเจนว่า "framework เปลี่ยนทีหลังมีต้นทุนสูงมาก เท่ากับเขียนใหม่"
— ตารางต้นทุนของ ADR-01 เองทำนายสถานการณ์นี้ไว้แล้ว

คำสั่งรอบนี้เปลี่ยนเงื่อนไขที่ ADR-01 ใช้ตัดสินใจโดยตรง: ADR-01 ประเมิน "Go +
HTMX" และปฏิเสธด้วยเหตุผลว่า **"เหมาะกับทีมที่ถนัด Go อยู่แล้วเท่านั้น"** — คำสั่ง
รอบนี้คือสัญญาณว่าเงื่อนไขนั้นเปลี่ยนไปแล้ว (มีข้อกำหนดจากภายนอก เช่น
หลักสูตร/ผู้ว่าจ้าง หรือทีมถนัด Go จริง) จึงไม่ใช่การเดาทิศทางใหม่ลอย ๆ แต่เป็น
การตอบสนองต่อเงื่อนไขที่เปลี่ยนซึ่ง ADR-01 ระบุไว้เองว่าจะทำให้ทางเลือกนี้กลับมา
น่าพิจารณาใหม่

**ทำไมต้องเป็น ADR ใหม่ ไม่ใช่แก้ ADR-01:** นี่ไม่ใช่การเพิ่มรายละเอียด (เหมือน
ตอนเพิ่ม ORM/VPS provider) แต่เป็นการเปลี่ยน**โครงสร้างระบบ** จาก "โค้ดชุดเดียว
ภาษาเดียว" เป็น "สองบริการคนละภาษา" — ตรงกับกฎของเทมเพลต ADR ของ repo นี้ที่ว่า
"การตัดสินใจไม่เคยถูกแก้ให้กลายเป็นคนละอย่าง เมื่อเปลี่ยนต้องเขียน ADR ใหม่"

ข้อกำหนดที่ยังบังคับทิศทางเหมือนเดิม (ยกมาจาก ADR-01 เพราะยังใช้ได้จริง):

| ข้อกำหนด | ที่มา | สิ่งที่บังคับ |
| --- | --- | --- |
| ออร์เดอร์ต้องถึงหน้าจอบาริสต้าภายใน 5 วินาที | `01` AC-4 | ต้อง push ไม่ใช่ poll — ต้องมี process ที่ค้างการเชื่อมต่อได้ |
| หน้าจอบาริสต้าหลุดแล้วกลับมาต้องดึงออร์เดอร์ค้างมาครบ | `01` §7 | ต้องเก็บสถานะฝั่งเซิร์ฟเวอร์ |
| เก็บ log จราจร 90 วัน แก้ย้อนหลังไม่ได้ | `02` BR-5, BR-5.2 | ต้องมีที่เก็บถาวรที่คุมได้ |
| เข้ารหัสขณะส่ง/จัดเก็บ | `02` BR-7 | ต้องคุม TLS และดิสก์ได้ |

ข้อสำคัญ: **Go เป็นตัวเลือกที่รองรับเงื่อนไขเหล่านี้ได้ดีเท่ากันหรือดีกว่า Node.js**
— `net/http` + goroutine รองรับ WebSocket ค้างการเชื่อมต่อจำนวนมากพร้อมกันได้
เป็นจุดแข็งของภาษานี้อยู่แล้ว ไม่ใช่การยอมเสียคุณสมบัติที่ ADR-01 ต้องการเพื่อ
ได้มาซึ่งภาษาที่ต้องการ

## ทางเลือกที่พิจารณา (ส่วนที่ผู้ใช้ให้เลือกเอง)

### Go web framework

| ทางเลือก | ข้อดี | ข้อเสีย | เหตุผลที่ไม่เลือก |
| --- | --- | --- | --- |
| **Gin** | ชุมชนใหญ่ที่สุดในบรรดา Go web framework, เอกสาร/ตัวอย่างสอนมากที่สุด, middleware สำเร็จรูปครบ (เหมาะกับทีมเล็กที่ต้องการของที่หาคำตอบได้เร็ว ตรงกับหลักการเดิมของ ADR-01 เรื่อง "ของที่มีเอกสารมาก") | ผูกกับ pattern ของ Gin เอง ย้าย framework ทีหลังต้องแก้ handler ทั้งหมด | — เลือกอันนี้ |
| chi | บาง เกาะ `net/http` ตรง ๆ ไม่มี magic, เข้ากับ library มาตรฐานง่ายที่สุด | ต้องประกอบ middleware เอง (logging, recovery, cors) มากกว่า Gin | ใกล้เคียงมาก เหมาะกับทีมที่อยากคุม stdlib เต็มที่ — ถ้าทีมมีคนถนัด Go มาก่อนควรพิจารณาใหม่ |
| Echo | สมดุลระหว่าง Gin กับ chi feature พอกัน Gin | ชุมชนเล็กกว่า Gin เล็กน้อย ไม่มีข้อได้เปรียบชัดเจนเหนือ Gin | ไม่มีเหตุผลชัดเจนที่จะเลือกเหนือ Gin ในบริบทนี้ |
| Fiber | เร็วที่สุด (fasthttp) | fasthttp ไม่ compat กับ `net/http` เต็มรูปแบบ — WebSocket library มาตรฐานหลายตัวคาด `net/http`, อาจมีปัญหาความเข้ากันได้ | ความเร็วที่ได้ไม่คุ้มกับความเสี่ยงเรื่อง WebSocket ซึ่งเป็นเงื่อนไขหลักของ AC-4 |

### WebSocket library

| ทางเลือก | ข้อดี | ข้อเสีย | เหตุผลที่ไม่เลือก |
| --- | --- | --- | --- |
| **gorilla/websocket** | ใช้กันแพร่หลายที่สุด ตัวอย่าง/บทเรียนมากที่สุด เข้ากับ `net/http` (และ Gin) ตรง ๆ | อยู่ในสถานะ maintenance mode (ไม่มี feature ใหม่ แต่ยังรับ security patch) | เอกสาร/ตัวอย่างที่มากกว่าสำคัญกว่าสำหรับทีมเล็ก — maintenance mode ไม่ใช่ deprecated |
| coder/websocket (เดิม nhooyr.io/websocket) | ทันสมัยกว่า, รองรับ context ดีกว่า, ยังพัฒนาต่อ | ชุมชน/ตัวอย่างน้อยกว่า gorilla มาก | ข้อดีทางเทคนิคจริง แต่แพ้เรื่องเอกสารสำหรับทีมเล็กที่ต้องหาคำตอบเอง |

### DB access ฝั่ง Go

| ทางเลือก | ข้อดี | ข้อเสีย | เหตุผลที่ไม่เลือก |
| --- | --- | --- | --- |
| **sqlc + pgx** | เขียน SQL ตรง ๆ (ใช้ schema ที่มีอยู่แล้วใน [[20260824-03-architecture-api-db-design|เอกสารออกแบบ]] ได้ทันที) แล้ว generate Go type-safe code — ไม่มี ORM magic ที่ต้องเรียนเพิ่ม | ต้องรัน code generation เป็นขั้นตอนใน build | — เลือกอันนี้ |
| GORM | เขียนน้อยกว่า มี auto-migration, เป็นที่นิยมสำหรับ CRUD เร็ว | ต้องแปลง schema ที่ออกแบบเป็น SQL ไว้แล้วให้เป็น Go struct tags แทน เพิ่มชั้นการแปลที่ไม่จำเป็น เพราะ schema จริงเขียนเป็น SQL ไว้ก่อนแล้ว | schema ที่มีอยู่แล้วเข้ากับแนวทาง sqlc โดยตรงกว่า ไม่ต้องแปลผ่าน ORM |
| pgx ตรง ๆ ไม่ใช้ sqlc | คุมได้เต็มที่สุด | เขียน boilerplate มาก ไม่มี type-safety ที่ generate ให้อัตโนมัติ | sqlc ให้ประโยชน์เดียวกันโดยลดงานเขียนมือ |

## ผลที่ตามมา

### สิ่งที่ได้

- backend และ frontend deploy/scale แยกกันได้ — ถ้า backend ต้องการทรัพยากรมากขึ้น
  (เช่น WebSocket connection จำนวนมากตอนเปิดร้าน) ไม่ต้องขยาย frontend ตามไปด้วย
- Go binary เดียวสำหรับ backend ไม่มี dependency runtime เยอะแบบ Node — ง่ายต่อ
  การ deploy บน VPS
- โค้ด backend และ frontend แยก concern ชัดเจนตั้งแต่โครงสร้าง ไม่ปนกันเหมือน
  Next.js API routes ที่ทำหน้าที่ทั้งสองอย่าง

### สิ่งที่ต้องแลก

- **ทีมต้องดูแลสองภาษา** (TypeScript + Go) แทนภาษาเดียว — ต้นทุนที่ ADR-01
  พยายามเลี่ยงไว้ตอนแรก แต่เป็นสิ่งที่คำสั่งรอบนี้ยอมรับแล้ว
- ต้องออกแบบสัญญา API ระหว่างสองบริการให้นิ่ง (versioning) เพราะเปลี่ยนแยกกันได้
  ถ้าไม่ระวังจะพังกันเอง
- deploy ต้องจัดการสอง process บน VPS เดียว (reverse proxy แยก route ไปสอง
  backend) เพิ่มความซับซ้อนของ infrastructure เทียบกับโค้ดชุดเดียวเดิม

### สิ่งที่ทำได้ยากขึ้นหลังจากนี้

- กลับไปรวมเป็นโค้ดชุดเดียวแบบ ADR-01 ภายหลังจะต้องเขียน backend ใหม่เป็น
  Next.js API routes ทั้งหมด — เท่ากับย้อนกลับ ไม่ใช่แค่ปรับ

## ต้นทุนของการเปลี่ยนใจ

เหมือนกับ ADR-01: **ภาษา backend เปลี่ยนทีหลัง = ต้นทุนสูงสุด เท่ากับเขียนใหม่**
ADR นี้เองก็อยู่ในหมวดนั้น — ควรถือว่าเป็นการตัดสินใจที่ **นิ่งแล้ว** เว้นแต่จะมี
เงื่อนไขภายนอกเปลี่ยนอีกครั้ง (เช่น ทีมจริงที่จะพัฒนาไม่มีใครถนัด Go เลย)

## สิ่งที่ทำได้ยังไม่ได้ตัดสินใจ

- [ ] ผู้ให้บริการ VPS รายใด และสเปคเท่าไร (สืบทอดจาก ADR-01 ยังไม่ตัดสินใจ)
- [ ] วิธีเข้ารหัสข้อมูลขณะจัดเก็บตาม BR-7 ของ `02` (สืบทอดจาก ADR-01)
- [ ] Reverse proxy ที่ใช้จัดการสอง process (nginx/Caddy) และ TLS termination
- [ ] Auth mechanism ระหว่าง frontend กับ backend (session cookie vs. JWT) —
      ยังไม่ตัดสินใจ ไม่ได้อยู่ในคำขอรอบนี้
