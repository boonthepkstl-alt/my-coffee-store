# ADR-02 — เลือกผู้ให้บริการชำระเงิน

> ✅ **สถานะ `ยอมรับแล้ว` (2026-08-24)** — ผู้ใช้ยืนยันตัวเลือกที่แนะนำ

## บริบท

`20260802-01` Q2 (ตัดสินใจแล้ว) กำหนดว่าลูกค้าจ่ายทันทีตอนยืนยันออร์เดอร์ผ่าน
PromptPay — ADR-01 ทิ้งไว้เป็นงานต่อเนื่องให้ตัดสินใจผู้ให้บริการจริง เพราะ
กระทบ BL-004 ตรง ๆ และเป็นเงื่อนไขของ AC-4 (ออร์เดอร์ต้องถึงจอบาริสต้าภายใน
5 วินาทีหลังจ่ายเงินสำเร็จ)

ข้อจำกัดที่ต้องอยู่ในกรอบ:

- ต้องรับ PromptPay QR ได้ (ตัดสินใจแล้วใน spec 01)
- ต้องมี webhook แจ้งผลการจ่ายเงิน เพราะ AC-4 นับเวลาจาก "จ่ายเงินสำเร็จ" ไม่ใช่
  จาก "ลูกค้ากดยืนยัน" — ถ้า gateway ไม่มี webhook จะทำ AC-4 ให้แม่นยำไม่ได้
- ทีมขนาดเล็ก ต้องการ SDK/เอกสารภาษาไทยหรืออังกฤษที่ใช้งานได้จริง ไม่ใช่ของที่ต้อง
  เดาเอง (สอดคล้องกับเหตุผลของ ADR-01)

## การตัดสินใจ

รับเงินผ่าน **PromptPay QR ผ่านผู้ให้บริการ payment gateway ของไทย** — ไม่ผูก
กับผู้ให้บริการรายใดรายหนึ่งเจาะจงในเอกสารนี้ (Omise/Opn, 2C2P, GB Prime Pay
ล้วนเข้าเกณฑ์) การเลือกผู้ให้บริการรายจริงเป็นการตัดสินใจเชิงพาณิชย์ (ค่าธรรมเนียม
สัญญา) ที่ควรทำตอนเริ่มพัฒนาจริง ไม่ใช่ตอนออกแบบสถาปัตยกรรม — สิ่งที่ ADR นี้
ตัดสินใจคือ **รูปแบบการเชื่อมต่อ (PromptPay QR + webhook)** ไม่ใช่ชื่อบริษัท

## ทางเลือกที่พิจารณา

| ทางเลือก | ข้อดี | ข้อเสีย | เหตุผลที่ไม่เลือก |
| --- | --- | --- | --- |
| **PromptPay QR ผ่าน gateway ไทย** | ลูกค้าไทยคุ้นเคยที่สุด ไม่มีข้อมูลบัตรเข้าระบบเลย (ดีต่อ PDPA/BR-7 ของสเปค 02 เรื่องเข้ารหัส) มี webhook รองรับ AC-4 | ต้องพึ่งบริการนอกสำหรับความสำเร็จของการจ่ายเงิน | — เลือกอันนี้ |
| รับเงินสดที่เคาน์เตอร์แทน | ไม่ต้องเชื่อม gateway เลย | ขัดกับ Q2 ของสเปค 01 ที่ตัดสินใจไปแล้วว่าจ่ายทันทีตอนยืนยันผ่านระบบ — จะต้องย้อนกลับไปแก้ requirement | เป็นการเปลี่ยน requirement ไม่ใช่ทางเลือกเชิง technical |
| ยังไม่เลือกผู้ให้บริการ ออกแบบ API แบบ abstract รอไว้ก่อน | ไม่บล็อกงานตอนนี้ | ทุกช่องที่เกี่ยวกับ webhook payload จะเป็น TBD จนกว่าจะเลือกจริง ทำให้ตาราง traceability ของ AC-4/AC-5 ไม่สมบูรณ์ | ผู้ใช้ยืนยันแนวทางที่แนะนำแล้ว ไม่มีเหตุผลให้ค้างไว้ |

## ผลที่ตามมา

### สิ่งที่ได้

- เส้นทาง "จ่ายเงิน → webhook → สร้างออร์เดอร์ยืนยัน" ชัดเจน ทำให้วัด AC-4 ได้จริง
- ไม่มีข้อมูลบัตรเครดิต/เดบิตไหลผ่านระบบของร้านเลย — ลดขอบเขต PCI และ PDPA
  ไปในตัว (ไม่ต้องมี BR-7 ของสเปค 02 ครอบคลุมข้อมูลบัตรเพิ่ม)

### สิ่งที่ต้องแลก

- ต้องมีค่าธรรมเนียมต่อรายการ (ยอมรับไว้แล้วตั้งแต่ Q2 ของสเปค 01)
- Uptime ของระบบขึ้นกับ uptime ของ gateway ด้วย — ถ้า gateway ล่ม ลูกค้าจ่ายเงิน
  ไม่ได้แม้ระบบร้านจะทำงานปกติ

### สิ่งที่ทำได้ยากขึ้นหลังจากนี้

- เปลี่ยนผู้ให้บริการภายหลังต้องแก้ webhook handler และอาจต้องย้ายข้อมูล
  `provider_ref` เก่า — ออกแบบ schema ให้เก็บ `provider` เป็นคอลัมน์แยกไว้แล้ว
  เพื่อลดผลกระทบ (ดูเอกสารออกแบบ schema)

## ต้นทุนของการเปลี่ยนใจ

**กลาง** — ถ้าเปลี่ยนผู้ให้บริการรายจริงภายหลัง (เช่น จาก Omise ไป 2C2P) กระทบแค่
ชั้น payment adapter และ webhook handler ไม่กระทบ schema หลักหรือ order flow
เพราะ schema ออกแบบให้ `provider`/`provider_ref` เป็นข้อมูลแยกจากตรรกะออร์เดอร์แต่แรก

      ไม่ใช่งานของ ADR นี้
