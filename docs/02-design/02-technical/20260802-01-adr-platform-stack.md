# ADR-01 — เลือกแพลตฟอร์มหลักของระบบ

> ✅ **สถานะ `ยอมรับแล้ว` (2026-08-02)** — ผู้ใช้ยืนยันตัวเลือกทั้งสี่ตามที่เสนอไว้
> (TypeScript + Next.js / Node.js long-running / PostgreSQL / VPS ในประเทศไทย)
> เขียนโค้ดอ้างอิงเอกสารนี้ได้แล้ว

> **หมายเหตุเรื่องขอบเขตของ ADR นี้**
> เทมเพลต ADR ของโปรเจกต์กำหนดว่า 1 เอกสาร = 1 การตัดสินใจ เอกสารนี้รวม framework,
> ฐานข้อมูล และ hosting ไว้ด้วยกันโดยเจตนา เพราะทั้งสามผูกกันแน่น — framework จำกัดตัวเลือก
> hosting และ hosting เป็นตัวกำหนดว่าทำ WebSocket แบบค้างการเชื่อมต่อได้หรือไม่ ซึ่งเป็นเงื่อนไข
> ของ AC-4 การแยกเป็นสามเอกสารจะได้ ADR ที่แต่ละฉบับเขียนว่า "ขึ้นกับอีกสองฉบับ" ซึ่งอ่านไม่รู้เรื่อง
> ส่วนผู้ให้บริการชำระเงินแยกเป็น ADR-02 เพราะเปลี่ยนได้โดยไม่กระทบส่วนอื่น

## บริบท

โปรเจกต์นี้**ยังไม่มีโค้ดเลย** ไม่มี package manifest ไม่มี build tooling ไม่มี test runner
ทุกอย่างหลังจากนี้ขึ้นอยู่กับการตัดสินใจนี้ จึงต้องตัดสินใจก่อนเขียนเอกสารออกแบบฉบับใดก็ตาม

ข้อกำหนดที่บังคับทิศทางของการเลือก:

| ข้อกำหนด | ที่มา | สิ่งที่บังคับ |
| --- | --- | --- |
| ลูกค้าสแกน QR แล้วเปิดเว็บบนมือถือตัวเอง ไม่ติดตั้งแอป | `01` Q1, BL-003 | ต้องเป็นเว็บที่โหลดเร็วบนมือถือและเน็ตร้าน |
| ออร์เดอร์ต้องถึงหน้าจอบาริสต้า **ภายใน 5 วินาที** | `01` AC-4 | ต้องมีการส่งข้อมูลแบบ push ไม่ใช่ให้หน้าจอ poll |
| หน้าจอบาริสต้าหลุดแล้วกลับมา ต้องดึงออร์เดอร์ค้างมาครบ | `01` ตาราง §7 | ต้องเก็บสถานะไว้ฝั่งเซิร์ฟเวอร์ ไม่พึ่งการเชื่อมต่อค้าง |
| ตัดเงินกับสร้างออร์เดอร์ต้องสำเร็จหรือล้มทั้งคู่ | `01` §7 แถว 2 | ต้องมี transaction ที่เชื่อถือได้ |
| รหัสผ่านเก็บแบบ hash เท่านั้น | `02` BR-6 | — |
| เข้ารหัสทั้งขณะส่งและขณะจัดเก็บ | `02` BR-7 | ต้องคุม TLS และการเข้ารหัสระดับดิสก์/ฐานข้อมูลได้ |
| เก็บ log จราจร 90 วัน แก้ย้อนหลังไม่ได้ | `02` BR-5, BR-5.2 | ต้องมีที่เก็บถาวรที่คุมได้ ไม่ใช่ log ที่หายเมื่อ redeploy |
| แจ้งเตือนก่อนพื้นที่ log เต็ม ห้ามลบก่อนครบ 90 วัน | `02` BR-5.4 | ต้องเข้าถึงระดับ filesystem/monitoring ได้ |
| GA4 ยิงหลังได้รับความยินยอมเท่านั้น | `03` BR-1 | ต้องคุมลำดับการโหลด script ฝั่ง client ได้ |

ข้อจำกัดที่ต้องอยู่ในกรอบ:

- ทีมขนาดเล็ก — ต้องเลือกของที่มีเอกสารและตัวอย่างมาก ไม่ใช่ของที่ต้องเดาเอง
- ร้านกาแฟร้านเดียว ปริมาณทราฟฟิกต่ำถึงปานกลาง ไม่ต้องออกแบบเพื่อสเกลใหญ่ตั้งแต่วันแรก
- **มีการโอนข้อมูลออกนอกประเทศอยู่แล้ว 1 ทางจาก Google Analytics** (`03` BL-017)
  การเพิ่มทางที่สองโดยไม่จำเป็นทำให้งานประเมินตาม PDPA หนักขึ้นเปล่า ๆ

## การตัดสินใจ

`[ตัดสินใจแล้ว 2026-08-02 — ผู้ใช้ยืนยันตามที่เสนอ]`

| ส่วน | เลือกใช้ |
| --- | --- |
| ภาษา | TypeScript |
| Framework | Next.js (App Router) — ใช้ทั้งเว็บลูกค้า หน้าจอบาริสต้า และ API ในโค้ดชุดเดียว |
| Runtime | Node.js แบบ long-running **ไม่ใช่ serverless** |
| Realtime | WebSocket บนเซิร์ฟเวอร์เดียวกัน |
| ฐานข้อมูล | PostgreSQL |
| Hosting | VPS ที่ตั้งอยู่ในประเทศไทย |

**ตรึงเวอร์ชันจริงตอนเริ่มโครงการ** และบันทึกกลับมาที่เอกสารนี้ — ผู้เขียนไม่ทราบว่า
เวอร์ชันล่าสุด ณ วันที่เริ่มพัฒนาคือเวอร์ชันใด จึงไม่ระบุเลขไว้ล่วงหน้าเพื่อไม่ให้เข้าใจผิด

ประเด็นที่ต้องเน้น: **Node.js แบบ long-running ไม่ใช่ serverless** เพราะ AC-4 ต้องการ push
ภายใน 5 วินาที และ BR-5 ต้องการ log ถาวร 90 วัน ทั้งสองอย่างขัดกับรูปแบบ serverless
ที่ไม่ค้างการเชื่อมต่อและระบบไฟล์หายเมื่อ deploy ใหม่

## ผลที่ตามมา

### สิ่งที่ได้

- โค้ดชุดเดียว ภาษาเดียว ครอบคลุมเว็บลูกค้า หน้าจอบาริสต้า และ API
- WebSocket รันบนเซิร์ฟเวอร์เดียวกับ API ทำให้ AC-4 (5 วินาที) ทำได้โดยไม่พ่วงบริการนอก
- ข้อมูลส่วนบุคคลอยู่ในประเทศไทย เหลือการโอนออกนอกประเทศเพียงทางเดียวคือ GA
  ทำให้งานตาม BL-017 แคบลงและอธิบายในนโยบายความเป็นส่วนตัวได้ง่ายขึ้น
- คุม log ระดับ filesystem ได้ ทำ BR-5, BR-5.2 และ BR-5.4 ได้ตรงไปตรงมา
- ควบคุมลำดับการโหลด script ฝั่ง client ได้เต็มที่ จำเป็นต่อ BR-1 ของ `03` ที่ห้ามยิง GA ก่อนยินยอม

### สิ่งที่ต้องแลก

- **ต้องดูแลเซิร์ฟเวอร์เอง** — OS patch, ต่ออายุ TLS, backup, monitoring, กู้คืนเมื่อล่ม
  นี่คือต้นทุนที่แท้จริงของการเลือกข้อนี้ ไม่ใช่รายละเอียดปลีกย่อย ถ้าทีมไม่มีเวลาส่วนนี้
  ควรกลับไปพิจารณา Vercel และยอมรับงาน PDPA ที่เพิ่มขึ้นแทน
- ต้องเขียน migration ฐานข้อมูลเองและมีวินัยกับมัน
- ไม่มีการสเกลอัตโนมัติ ถ้าทราฟฟิกพุ่งเกินเครื่องต้องขยายด้วยมือ
- TypeScript ทำให้มีขั้น build เพิ่ม ผู้ที่ไม่คุ้นจะรู้สึกช้าลงในช่วงแรก

### สิ่งที่ทำได้ยากขึ้นหลังจากนี้

- ย้ายไป serverless ภายหลังจะติดที่ WebSocket และ log ถาวร ต้องออกแบบสองส่วนนั้นใหม่
- เปลี่ยนไปใช้ภาษาอื่นฝั่งเซิร์ฟเวอร์เท่ากับเขียนใหม่ทั้งหมด
- ถ้าภายหลังต้องรองรับหลายสาขา จะต้องกลับมาทบทวนเรื่อง hosting และการแยกข้อมูลต่อสาขา

## ต้นทุนของการเปลี่ยนใจ

| เปลี่ยนอะไร | ต้นทุนถ้าเปลี่ยนหลังเริ่มพัฒนา |
| --- | --- |
| Hosting (VPS → Vercel หรือกลับกัน) | **ต่ำถึงกลาง** ถ้ายังไม่ผูกกับของเฉพาะเจ้า — แต่ต้องออกแบบ WebSocket และที่เก็บ log ใหม่ |
| ฐานข้อมูล (Postgres → MySQL) | **กลาง** ถ้าใช้ผ่าน ORM และไม่ใช้ feature เฉพาะของ Postgres มาก |
| Framework (Next.js → อื่น) | **สูงมาก** เท่ากับเขียนใหม่ |
| ภาษา (TypeScript → อื่น) | **สูงสุด** เขียนใหม่ทั้งระบบ |

สองแถวล่างกลับตัวยากที่สุด จึงเป็นสองข้อที่ควรถกให้จบก่อนเขียนบรรทัดแรก
สองแถวบนเปลี่ยนได้ภายหลังโดยเจ็บพอทน ถ้าไม่ผูกกับของเฉพาะเจ้าตั้งแต่ต้น
