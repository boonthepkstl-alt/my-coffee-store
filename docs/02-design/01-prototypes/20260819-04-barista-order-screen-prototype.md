# หน้าจอรับออร์เดอร์สำหรับบาริสต้า — Prototype Specification

## 1. ขอบเขต

1 หน้าจอ: คิวออร์เดอร์ — ตรงกับ journey §5

## 2. Screen: คิวออร์เดอร์

**บทบาทที่ใช้:** บาริสต้า
**เข้าถึงจาก:** เปิดทิ้งไว้ตลอดกะการทำงาน ไม่ได้ navigate มาจากหน้าอื่นในระบบนี้
**ไปต่อที่:** ไม่มี — เป็นหน้าจอเดียวของ feature นี้

### Layout

Device context: จอบาริสต้า/พนักงาน (DESIGN.md §2) — จอขนาดใหญ่ ดูจากระยะไกล
ระหว่างทำงาน ต้องอ่านง่ายแบบ "เหลือบตา" ไม่ใช่จ้องนาน (ตาม DESIGN.md §1
Visual Direction ที่อนุมานจาก US-5)
โครง: เต็มพื้นที่จอเป็นคิวออร์เดอร์ ไม่มี header/navigation ที่ซับซ้อน เพราะเป็น
หน้าจอเดียวที่เปิดค้างไว้

### Components ที่ใช้

| Component (ชื่อจาก DESIGN.md §3) | Purpose บนหน้าจอนี้ | Variant/เนื้อหา |
| --- | --- | --- |
| Table **หรือ** Card | แสดงออร์เดอร์แต่ละใบในคิว | **ยังไม่ตัดสิน — ช่องว่างเดียวกับที่พบใน BL-001 (Table vs Card) ดู §4** |
| Badge | สถานะออร์เดอร์: รับแล้ว / เสร็จแล้ว | |
| Button | ปุ่ม "เสร็จแล้ว" ต่อออร์เดอร์ | |

### Navigation

ไม่มีการ navigate ออกจากหน้าจอนี้ในระบบ — เป็น single-screen kiosk-style สำหรับ
feature นี้ (สเปคไม่ได้พูดถึงหน้าจออื่นสำหรับบาริสต้า)

### Interaction

- ออร์เดอร์ใหม่ปรากฏเองในคิวเมื่อชำระเงินสำเร็จ (push, ไม่ใช่ผู้ใช้กระทำ) — AC-4
- กดปุ่ม "เสร็จแล้ว" ที่ออร์เดอร์ใด → ออร์เดอร์นั้นออกจากคิวที่รอทำทันที — AC-6

### States

| State | Trigger | พฤติกรรมที่ต้องมี (จากสเปค) | UI treatment |
| --- | --- | --- | --- |
| Default | มีออร์เดอร์รอทำอยู่ในคิว | US-5: เห็นออร์เดอร์ใหม่พร้อมหมายเลขโต๊ะ | TBD |
| Loading | เปิดหน้าจอครั้งแรก / โหลดคิว | โดยนัย ไม่มีใน AC ตรง ๆ | TBD |
| Empty | ไม่มีออร์เดอร์ค้างในคิว | ไม่มีในสเปคตรง ๆ — เพิ่มเพราะ AI Design Rule 8 ต้องพิจารณาครบ | TBD |
| New order arrived | ชำระเงินสำเร็จ | AC-4: ต้องปรากฏภายใน 5 วินาที — **นี่คือ AC ที่มีตัวเลขวัดผลได้จริง ต้อง test ตรงเวลา ไม่ใช่ "เร็ว ๆ"** | TBD |
| Completed | กด "เสร็จแล้ว" | AC-6: สถานะเปลี่ยน ออกจากคิวที่รอทำ | TBD |
| Reconnect/Resync | หน้าจอหลุดการเชื่อมต่อแล้วกลับมา | สเปค §7: ต้องดึงออร์เดอร์ที่ค้างมาแสดงครบ ไม่มีใบตกหล่น — **DESIGN.md ไม่มี pattern นี้ ดู §4** | TBD |

### Responsive

รองรับเฉพาะ device context "จอบาริสต้า/พนักงาน" — journey ระบุไว้แล้วว่าไม่มี
ข้อกำหนดให้ใช้บนมือถือลูกค้า

### Accessibility

`TBD` — ไม่มีข้อกำหนดในสเปคหรือ DESIGN.md (ช่องว่างที่รู้อยู่แล้ว)
ข้อสังเกตเพิ่มเติมที่ควรพิจารณาเมื่อมีการตัดสินใจ accessibility จริง: หน้าจอนี้
ใช้งานขณะทำงานมือไม่ว่าง (ชงกาแฟไปด้วย) — การกดปุ่ม "เสร็จแล้ว" ควรพิจารณา
ขนาด touch target ที่ใหญ่พอ แต่นี่เป็นข้อสังเกต ไม่ใช่ข้อกำหนดที่ยืนยันแล้ว

## 3. สิ่งที่ต้องกลับไปเพิ่มใน DESIGN.md

- **Table vs Card สำหรับคิวออร์เดอร์** — ช่องว่างเดียวกับที่ prototype ของ BL-001
  พบแล้ว (Table vs Card สำหรับรายการเมนู) ยืนยันอีกครั้งว่าเป็น pattern เดียวกัน
  ที่ต้องตัดสินใจครั้งเดียวแล้วใช้ร่วมกันทั้งสอง feature ไม่ใช่ตัดสินแยกกัน
- **Reconnect/Resync pattern** — journey §7 ระบุไว้แล้วว่าไม่มีใน DESIGN.md
  ยืนยันอีกครั้งที่ระดับ prototype — ต่างจาก Offline/Network Error ทั่วไปเพราะ
  ต้อง "ดึงข้อมูลค้างมาแสดงครบ" ไม่ใช่แค่แจ้งเตือนสถานะ
- **Empty/Loading state ทั่วไป** — ไม่มี pattern (ช่องว่างที่รู้อยู่แล้ว ไม่ใช่ของใหม่)

## 4. คำถามที่ยังค้าง
