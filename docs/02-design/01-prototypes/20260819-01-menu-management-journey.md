# จัดการเมนู ราคา และการเปิด/ปิดขายรายรายการ — User Journey

> เอกสารนี้สร้างจากการรัน skill `feature-journey` แบบ pilot ครั้งแรก
> (เขียนด้วยมือตามขั้นตอนของ skill เพราะ skill เพิ่งสร้างในรอบนี้ ยังไม่ผ่าน
> `/reload-skills` — เนื้อหาถูกต้องตามกระบวนการเดียวกับที่ skill จะทำเมื่อถูกเรียกจริง)

## 1. ขอบเขตของ Journey นี้

ครอบคลุม **BL-001** เท่านั้น — การจัดการรายการเมนู ราคา และการเปิด/ปิดขายรายเมนู
โดยพนักงานหน้าร้านและเจ้าของร้าน

**ไม่ครอบคลุม:** การสั่งซื้อของลูกค้า (BL-003), หน้าจอบาริสต้า (BL-005),
การสร้าง/จัดการบัญชีผู้ใช้ (BL-006 — journey แยกต่างหาก แต่ journey นี้
**อ้างอิงสิทธิ์** ที่ BL-006 ต้องกำหนดไว้ เพราะ BR-7 บังคับว่าเฉพาะเจ้าของร้าน
แก้ราคาได้)

## 2. ผู้ใช้และเป้าหมาย

ดึงจากสเปค §3/§4 ตรง ๆ:

| ผู้ใช้ | เป้าหมาย | ที่มา |
| --- | --- | --- |
| พนักงานหน้าร้าน | ปิดเมนูที่ของหมดได้ทันที เพื่อไม่ให้ลูกค้าสั่งของที่ทำไม่ได้ | US-6 |
| เจ้าของร้าน | แก้ไขเมนูและราคาได้เอง เพื่อไม่ต้องรอผู้พัฒนา | US-7 |

## 3. เส้นทางหลัก (Happy Path)

```text
1. พนักงาน/เจ้าของร้านล็อกอินเข้าระบบจัดการร้าน         [หน้าจอ: เข้าสู่ระบบ]  [BL-006, นอกขอบเขต journey นี้]
2. เปิดหน้าจัดการเมนู เห็นรายการเมนูทั้งหมดพร้อมสถานะเปิด/ปิดขาย  [หน้าจอ: รายการเมนู]  [US-6, US-7]
3ก. พนักงานกดปิดขายเมนูที่ของหมด → สถานะเปลี่ยนทันที        [หน้าจอ: รายการเมนู]  [US-6, BR-3, AC-2, AC-7]
3ข. เจ้าของร้านกดแก้ไขเมนู → เปิดฟอร์มแก้ไข → แก้ชื่อ/ราคา/รูป → บันทึก
                                                          [หน้าจอ: แก้ไขเมนู]  [US-7, BR-4]
4. ระบบยืนยันการบันทึกสำเร็จ กลับไปหน้ารายการเมนู         [หน้าจอ: รายการเมนู]
```

## 4. เส้นทางรอง / กรณีขอบ

ดึงจากสเปค §7 — แถวเดียวที่เกี่ยวข้องกับ feature นี้โดยตรง:

| กรณีจากสเปค §7 | ผลกระทบต่อ journey นี้ |
| --- | --- |
| เมนูถูกปิดขายระหว่างที่ลูกค้ากำลังเลือก | เป็นผลข้าง**ของ**การกระทำในขั้น 3ก — journey ฝั่งลูกค้า (BL-003) ต้องรับรู้การเปลี่ยนแปลงนี้ ไม่ใช่หน้าที่ของ journey นี้โดยตรง แต่ **ขั้น 3ก ต้อง sync สถานะแบบทันที** ไม่ใช่ล่าช้า |

กรณีขอบเพิ่มเติมที่สเปค §7 ไม่ได้ระบุแต่ journey นี้ต้องคำนึงถึงเพราะเป็นผลจาก BR-7:

- **พนักงาน (ไม่ใช่เจ้าของร้าน) พยายามแก้ราคา** — ต้องถูกปฏิเสธตาม BR-7/AC-8
  ~~นี่คือ Permission State ที่ DESIGN.md ยังไม่มี pattern จริง~~ **ตัดสินใจแล้ว
  2026-08-19 — ดู DESIGN.md §3**: ซ่อนปุ่มเป็นค่าเริ่มต้น (layer 1) + Alert
  แบบ inline เมื่อมีการเรียกตรงถึง backend (layer 2, backstop) การซ่อนปุ่ม
  ไม่ใช่การแทนที่การปฏิเสธของระบบ — backend ยังปฏิเสธเสมอตาม AC-8 ไม่ว่า UI
  จะแสดงอะไร

## 5. หน้าจอที่เกี่ยวข้อง

| หน้าจอ | บทบาทที่ใช้ | Component ที่ต้องมี (อ้างจาก DESIGN.md §3) | สถานะที่ต้องมี |
| --- | --- | --- | --- |
| รายการเมนู | พนักงาน, เจ้าของร้าน | Table (ตัดสินแล้ว 2026-08-19), Switch (สลับเปิด/ปิดขาย — ตัดสินแล้ว 2026-08-19), Badge (สถานะ "ของหมด"), Alert (backstop สำหรับ Permission layer 2) | Default, Loading, Empty (ยังไม่มีเมนูเลย), Permission (ปุ่มแก้ราคาซ่อนสำหรับพนักงานทั่วไป — ตัดสินแล้ว 2026-08-19) |
| แก้ไขเมนู | เจ้าของร้านเท่านั้น | Input (ชื่อ/ราคา), Button (บันทึก/ยกเลิก) | Default, Validation, Loading (ระหว่างบันทึก), Error (บันทึกไม่สำเร็จ), Success |
| ~~ปฏิเสธสิทธิ์ (พนักงานพยายามแก้ราคา)~~ | — | — | **ยุบแล้ว 2026-08-19** — Permission State ไม่ใช่หน้าแยก ย้ายไปเป็น state ของหน้ารายการเมนู (ซ่อนปุ่ม + Alert backstop) ดู DESIGN.md §3 |

## 6. Non-goals ของ Journey นี้

- ไม่รวมการตัดสต๊อกอัตโนมัติ (ตัดทิ้งแล้วตาม Q4 ของสเปค — เฟสนี้ปิดขายด้วยมือเท่านั้น)
- ไม่รวมรายงานยอดขายของแต่ละเมนู (out of scope ของสเปค 01 ทั้งฉบับ)
- ไม่รวมการสร้าง/ลบบัญชีพนักงาน (เป็นของ BL-006)

## 7. สิ่งที่ต้องกลับไปเพิ่มใน requirement หรือ DESIGN.md

- ~~DESIGN.md ยังไม่มี Permission State pattern จริง~~ — **ตัดสินแล้ว 2026-08-19**
  (ซ่อนปุ่ม + Alert backstop, ดู DESIGN.md §3 และ §7 Design Decisions)
- **สเปคไม่ได้ระบุว่าลบเมนูออกได้ไหม หรือทำได้แค่ปิดขาย** — US-7 พูดถึง "แก้ไขเมนู"
  เท่านั้น ไม่ได้พูดถึงการลบ journey นี้จึงสมมติว่า**ไม่มีการลบเมนู มีแต่ปิดขาย**
  ตามหลัก never-delete ของ repo (docs/00-archived/index.md) — แต่นี่คือสมมติฐาน
  ที่ควรยืนยัน ไม่ใช่ข้อเท็จจริงจากสเปค
