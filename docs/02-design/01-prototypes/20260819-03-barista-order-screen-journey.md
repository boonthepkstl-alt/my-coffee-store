# หน้าจอรับออร์เดอร์สำหรับบาริสต้า — User Journey

## 1. ขอบเขตของ Journey นี้

ครอบคลุม **BL-005** เท่านั้น — หน้าจอที่บาริสต้าใช้ดูออร์เดอร์ใหม่และปิดงาน

**ไม่ครอบคลุม:** การสั่งซื้อของลูกค้า (BL-003), การชำระเงิน (BL-004),
การจัดการเมนู (BL-001 — journey แยกแล้ว)

## 2. ผู้ใช้และเป้าหมาย

ดึงจากสเปค §3/§4 ตรง ๆ:

| ผู้ใช้ | เป้าหมาย | ที่มา |
| --- | --- | --- |
| บาริสต้า | เห็นออร์เดอร์ใหม่พร้อมหมายเลขโต๊ะบนหน้าจอเดียว เพื่อทำงานตามลำดับได้ | US-5 |

## 3. เส้นทางหลัก (Happy Path)

```text
1. บาริสต้าเปิดหน้าจอทิ้งไว้ตลอดกะการทำงาน                    [หน้าจอ: คิวออร์เดอร์]
2. ลูกค้ายืนยันออร์เดอร์และชำระเงินสำเร็จ (นอกขอบเขต journey นี้ — BL-003/004)
3. ออร์เดอร์ใหม่ปรากฏบนหน้าจอคิวภายใน 5 วินาที พร้อมหมายเลขโต๊ะ  [หน้าจอ: คิวออร์เดอร์]  [AC-4]
4. บาริสต้าทำเครื่องดื่มตามคิว                                 [หน้าจอ: คิวออร์เดอร์]  [US-5]
5. บาริสต้ากด "เสร็จแล้ว" ที่ออร์เดอร์นั้น                       [หน้าจอ: คิวออร์เดอร์]  [AC-6]
6. ออร์เดอร์ออกจากคิวที่รอทำ สถานะเปลี่ยนเป็นเสร็จแล้ว           [หน้าจอ: คิวออร์เดอร์]  [AC-6]
```

## 4. เส้นทางรอง / กรณีขอบ

ดึงจากสเปค §7 — แถวที่เกี่ยวข้องกับ feature นี้โดยตรง:

| กรณีจากสเปค §7 | ผลกระทบต่อ journey นี้ |
| --- | --- |
| หน้าจอบาริสต้าหลุดการเชื่อมต่อ | เมื่อกลับมาต้องดึงออร์เดอร์ที่ค้างมาแสดงครบ ไม่มีใบตกหล่น — **ต้องมี resync mechanism ตอนเชื่อมต่อกลับ ไม่ใช่แค่รอ realtime event ถัดไป** |
| ชำระเงินสำเร็จแต่ระบบล่มก่อนบันทึกออร์เดอร์ | ต้องกู้คืนออร์เดอร์ได้ หรือแจ้งพนักงานให้ตรวจสอบ — journey นี้รับผลกระทบทางอ้อม: ถ้าออร์เดอร์กู้คืนมาช้า บาริสต้าจะไม่เห็นในคิวจนกว่าจะกู้คืนเสร็จ |

กรณีขอบเพิ่มเติมที่ไม่ได้อยู่ในสเปค §7 ตรง ๆ แต่จำเป็นต่อ journey นี้:

- **มีออร์เดอร์หลายใบเข้าคิวพร้อมกัน** — สเปคไม่ได้ระบุลำดับการแสดงผล (เรียงตามเวลา
  ยืนยัน หรือมีลำดับความสำคัญ) — ดูหัวข้อ 8
- **บาริสต้ากด "เสร็จแล้ว" ผิดใบ** — สเปคไม่ได้ระบุว่ากดยกเลิกได้ไหม — ดูหัวข้อ 8

## 5. หน้าจอที่เกี่ยวข้อง

| หน้าจอ | บทบาทที่ใช้ | Component ที่ต้องมี (อ้างจาก DESIGN.md §3) | สถานะที่ต้องมี |
| --- | --- | --- | --- |
| คิวออร์เดอร์ | บาริสต้า | Table **หรือ** Card (DESIGN.md ระบุไว้แล้วว่ายังไม่ตัดสิน — เป็นช่องว่างเดียวกับที่พบใน BL-001), Badge (สถานะออร์เดอร์: รับแล้ว/เสร็จแล้ว), Button ("เสร็จแล้ว" ต่อออร์เดอร์) | Default, Loading (ตอนเปิดหน้าจอครั้งแรก), Empty (ไม่มีออร์เดอร์ค้าง), Offline/Reconnect (ตาม §4) |

## 6. Non-goals ของ Journey นี้

- ไม่รวมการแก้ไข/ยกเลิกออร์เดอร์โดยบาริสต้า (สเปคพูดถึงแค่ "กดปิดงานเมื่อทำเสร็จ" ใน US-5 ไม่ได้พูดถึงการแก้ไข)
- ไม่รวมการแจ้งเตือนเสียง/การสั่นของอุปกรณ์เมื่อออร์เดอร์ใหม่เข้า (ไม่มีในสเปค)
- ไม่รวมการดูประวัติออร์เดอร์ที่เสร็จไปแล้ว (out of scope ของสเปค 01 ทั้งฉบับ — ไม่มีรายงานยอดขาย)

## 7. สิ่งที่ต้องกลับไปเพิ่มใน requirement หรือ DESIGN.md

- **DESIGN.md ยังไม่มี pattern สำหรับ "resync หลังหลุดการเชื่อมต่อ"** — ต่างจาก
  Offline state ทั่วไป (ที่มีอยู่แล้วสำหรับฝั่งลูกค้า) เพราะฝั่งนี้ต้อง "ดึงข้อมูลที่ค้าง
  มาแสดงครบ" ไม่ใช่แค่แจ้งว่าออฟไลน์ — เป็น pattern คนละแบบ ควรบันทึกแยกจาก
  Offline / Network Error ที่มีอยู่ใน DESIGN.md §3
- **ลำดับการแสดงผลออร์เดอร์ในคิวไม่มีข้อกำหนด** — เรียงตามเวลา หรือมีลำดับความสำคัญ
  ไม่มีสเปคระบุ ต้องยืนยันก่อนออกแบบ layout ของคิว

## 8. คำถามที่ยังค้าง

- [ ] ลำดับการแสดงผลออร์เดอร์หลายใบในคิว (FIFO หรือมีการจัดลำดับความสำคัญ?)
- [ ] บาริสต้ากด "เสร็จแล้ว" ผิดใบ แก้ไข/ย้อนกลับได้ไหม
- [ ] pattern การ resync หลังหลุดการเชื่อมต่อ — ยังไม่มีใน DESIGN.md (ดูหัวข้อ 7)
