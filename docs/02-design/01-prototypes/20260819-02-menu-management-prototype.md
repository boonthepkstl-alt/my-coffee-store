# จัดการเมนู ราคา และการเปิด/ปิดขายรายรายการ — Prototype Specification

> สร้างจากการรัน skill `prototype` แบบ pilot (เขียนด้วยมือตามขั้นตอนของ skill
> เพราะ skill ยังไม่ผ่าน `/reload-skills` ในรอบนี้)

## 1. ขอบเขต

3 หน้าจอ ตรงกับ journey §5: รายการเมนู, แก้ไขเมนู, ปฏิเสธสิทธิ์

## 2. Screen: รายการเมนู

**บทบาทที่ใช้:** พนักงานหน้าร้าน, เจ้าของร้าน
**เข้าถึงจาก:** journey ขั้น 2 (หลังล็อกอิน)
**ไปต่อที่:** แก้ไขเมนู (เจ้าของร้านเท่านั้น) / ปฏิเสธสิทธิ์ (พนักงานที่พยายามแก้ราคา)

### Layout

Device context: จอบาริสต้า/พนักงาน (DESIGN.md §2) — จอขนาดใหญ่กว่ามือถือลูกค้า
โครง: header (ชื่อร้าน/ผู้ใช้) → รายการเมนูเต็มพื้นที่ → ไม่มี footer action
(การกระทำอยู่ที่แต่ละแถว ไม่ใช่ปุ่มรวมด้านล่าง)

### Components ที่ใช้

| Component (ชื่อจาก DESIGN.md §3) | Purpose บนหน้าจอนี้ | Variant/เนื้อหา |
| --- | --- | --- |
| Table | แสดงรายการเมนูทั้งหมด | ตัดสินแล้ว 2026-08-19 (DESIGN.md §3) — รายการเมนูเป็นข้อมูลแถวสม่ำเสมอ (ชื่อ/ราคา/สถานะ/ปุ่ม) เข้าเกณฑ์ Table |
| Switch **หรือ** Checkbox | สลับเปิด/ปิดขายรายเมนู | **ยังไม่ตัดสินว่าแบบใด — DESIGN.md §3 ระบุไว้แล้วว่าเป็นช่องว่าง** |
| Badge | แสดงสถานะ "ของหมด" บนรายการที่ปิดขาย | |
| Button | ปุ่ม "แก้ไข" ต่อแถว (แสดงเฉพาะเจ้าของร้าน — ดู Permission ด้านล่าง) | |

### Navigation

กดปุ่ม "แก้ไข" ที่แถวใด → ไปหน้าแก้ไขเมนู ของรายการนั้น
ไม่มีปุ่มย้อนกลับพิเศษ — เป็นหน้าแรกของโมดูลนี้

### Interaction

- สลับสถานะเปิด/ปิดขาย → สถานะเปลี่ยนทันทีที่หน้าจอ (optimistic) ไม่ต้องกดยืนยัน
  (สเปคไม่ได้ระบุว่าต้องมี confirmation สำหรับการปิดขาย — ต่างจากการลบ ซึ่งยังไม่มีอยู่จริง)
- กด "แก้ไข" → ไปหน้าแก้ไขเมนู (เฉพาะเจ้าของร้าน) หรือเห็น Permission State (พนักงาน)

### States

| State | Trigger | พฤติกรรมที่ต้องมี (จากสเปค) | UI treatment |
| --- | --- | --- | --- |
| Default | โหลดรายการเมนูสำเร็จ | AC-2: แสดงเฉพาะรายการที่เปิดขายอยู่ในมุมมองลูกค้า — **แต่หน้าจอนี้คือมุมมองพนักงาน ต้องเห็นทั้งเปิด/ปิดขาย** (สเปคไม่ได้แยกมุมมองนี้ชัดเจน — บันทึกไว้ §4) | TBD (DESIGN.md ยังไม่มี token/pattern) |
| Loading | กำลังโหลดรายการ | ไม่มีในสเปคตรง ๆ แต่จำเป็นโดยนัย | TBD |
| Empty | ยังไม่มีเมนูเลย (ร้านเพิ่งเริ่มตั้งระบบ) | ไม่มีในสเปค — สถานะที่เพิ่มขึ้นเพราะ prototype ต้องพิจารณาครบ (AI Design Rule 8) | TBD |
| Sold-out toggled | พนักงานปิดขายรายการ | AC-7: ลูกค้าที่เปิดหน้าเมนูอยู่ต้องสั่งรายการนั้นไม่สำเร็จ — **หน้าจอนี้แค่ต้อง sync ทันที ผลกระทบฝั่งลูกค้าอยู่นอกขอบเขต** | TBD |
| Permission (พนักงานพยายามแก้ราคา) | พนักงานกดปุ่ม "แก้ไข" | AC-8: ระบบต้องปฏิเสธ | ไปหน้า "ปฏิเสธสิทธิ์" — ดู Screen 3 |

### Responsive

รองรับ device context "จอบาริสต้า/พนักงาน" เท่านั้นตาม journey — ไม่มีข้อกำหนด
ให้ใช้บนมือถือลูกค้า ดังนั้นไม่ต้องออกแบบ portrait/มือถือสำหรับหน้าจอนี้

### Accessibility

`TBD` — ไม่มีข้อกำหนดใน DESIGN.md หรือสเปค (ช่องว่างที่รู้อยู่แล้ว)

## 3. Screen: แก้ไขเมนู

**บทบาทที่ใช้:** เจ้าของร้านเท่านั้น (BR-7)
**เข้าถึงจาก:** ปุ่ม "แก้ไข" บนหน้ารายการเมนู
**ไปต่อที่:** กลับไปหน้ารายการเมนูเมื่อบันทึกสำเร็จหรือกดยกเลิก

### Layout

ฟอร์มเดี่ยว ไม่มี sidebar — เนื้อหาหลักคือฟิลด์แก้ไข

### Components ที่ใช้

| Component | Purpose | Variant |
| --- | --- | --- |
| Input | ชื่อเมนู, ราคา | |
| Button | บันทึก / ยกเลิก | |

### Navigation

บันทึกสำเร็จ → กลับหน้ารายการเมนู; ยกเลิก → กลับหน้ารายการเมนูโดยไม่บันทึก

### Interaction

กดบันทึก → validate → submit → loading → success (กลับหน้ารายการ) หรือ error (อยู่หน้าเดิม)

### States

| State | Trigger | พฤติกรรมที่ต้องมี | UI treatment |
| --- | --- | --- | --- |
| Validation | กรอกราคาไม่ถูกต้อง (เช่น ติดลบ, ไม่ใช่ตัวเลข) | ไม่มีกฎ validation ในสเปค — **ช่องว่าง ดู §4** | TBD |
| Loading | ระหว่างบันทึก | โดยนัย | TBD |
| Error | บันทึกไม่สำเร็จ | โดยนัย (ไม่มีในสเปคตรง ๆ) | TBD |
| Success | บันทึกสำเร็จ | BR-4: ราคาใหม่มีผลกับออร์เดอร์ใหม่เท่านั้น ไม่กระทบออร์เดอร์เดิม | TBD |

### Responsive

จอบาริสต้า/พนักงาน (เดียวกับ Screen 1)

### Accessibility

`TBD`

## 4. Screen: ปฏิเสธสิทธิ์

**บทบาทที่ใช้:** พนักงาน (ที่พยายามแก้ราคา)
**เข้าถึงจาก:** กดปุ่ม "แก้ไข" บนหน้ารายการเมนูโดยไม่ใช่เจ้าของร้าน
**ไปต่อที่:** กลับหน้ารายการเมนู

### Layout, Components, Navigation, Interaction

**ยังตัดสินใจไม่ได้** — journey §7/§8 ระบุไว้แล้วว่า DESIGN.md ไม่มี Permission
State pattern จริง จึงไม่ทราบว่าควรเป็นหน้าแยก, Alert แบบ inline, หรือ Dialog
เอกสารนี้เขียนเป็น "หน้าแยก" ชั่วคราวเพื่อให้ traceability ครบ **แต่ไม่ใช่การตัดสินใจ
จริง** — ต้องยืนยันก่อนใช้งาน

### States

| State | Trigger | พฤติกรรมที่ต้องมี | UI treatment |
| --- | --- | --- | --- |
| Permission denied | พนักงานพยายามแก้ราคา | AC-8: ระบบต้องปฏิเสธ | TBD — ดูหมายเหตุด้านบน |

## 5. สิ่งที่ต้องกลับไปเพิ่มใน DESIGN.md

- ~~Table vs Card สำหรับรายการเมนู~~ — **ตัดสินแล้ว 2026-08-19: Table** (ดู DESIGN.md §3
  และ §7 Design Decisions)
- **Switch vs Checkbox สำหรับสลับเปิด/ปิดขาย** — DESIGN.md §3 ระบุไว้แล้วว่าเป็น
  ช่องว่าง (`TBD` ซึ่ง control) ไม่ใช่เรื่องใหม่ที่ prototype นี้พบ
- **Permission State pattern** — ยังไม่มีเลยใน DESIGN.md แม้แต่แนวทางคร่าว ๆ
  นี่คือ gap ที่ prototype นี้เจอจริงเป็นครั้งแรก (ตรงกับที่ DESIGN.md §3 เตือนไว้)
- **Loading / Empty / Error state ทั่วไป** — ไม่มี pattern ที่กำหนดไว้เลย
