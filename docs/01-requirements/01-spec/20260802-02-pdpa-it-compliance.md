# การปฏิบัติตาม PDPA และกฎหมาย IT

> ⚠️ **เอกสารนี้ไม่ใช่คำแนะนำทางกฎหมาย**
> เขียนโดยผู้ที่ไม่ใช่นักกฎหมาย เพื่อใช้เป็นจุดตั้งต้นในการคุยกับที่ปรึกษากฎหมายเท่านั้น
> **ต้องให้ที่ปรึกษากฎหมายตรวจสอบก่อนนำไปใช้จริง** — PDPA มีโทษปรับทางปกครองสูงสุด 5 ล้านบาท
> และบางกรณีมีโทษอาญา การอ้างอิงมาตราต่าง ๆ ด้านล่างต้องได้รับการยืนยันความถูกต้องอีกครั้ง

> ⚠️ **เอกสารยังเป็นร่าง** — คำถาม 4 ข้อในหัวข้อ 8 ยังไม่ได้รับคำตอบ
> เนื้อหาเขียนบนสมมติฐานที่ทำเครื่องหมาย `[สมมติฐาน]` ไว้

## 1. ที่มาและปัญหา

ระบบรับออร์เดอร์จากโต๊ะใน [[20260802-01-table-self-ordering|20260802-01]] เป็นระบบออนไลน์
ที่ให้บริการแก่บุคคลทั่วไปในประเทศไทย จึงอยู่ภายใต้กฎหมายอย่างน้อย 2 ฉบับ

- **พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA)** — บังคับใช้เต็มรูปแบบตั้งแต่ 1 มิถุนายน 2565
- **พ.ร.บ. ว่าด้วยการกระทำความผิดเกี่ยวกับคอมพิวเตอร์ พ.ศ. 2550 (แก้ไขเพิ่มเติม พ.ศ. 2560)**

เอกสาร `20260802-01` ระบุเรื่องกฎหมายไว้เพียงในคำถามที่ยังค้าง (Q6) เท่านั้น ยังไม่มีข้อกำหนดจริง
หากพัฒนาระบบไปก่อนโดยไม่ออกแบบเรื่องนี้ตั้งแต่ต้น การแก้ย้อนหลังจะมีต้นทุนสูงกว่ามาก
เพราะกระทบตั้งแต่โครงสร้างฐานข้อมูลไปจนถึงหน้าจอผู้ใช้

> **คำขอเดิมจากผู้ใช้:**
> "เพิ่มเติมในส่วนของข้อกฎหมาย IT และ PDPA"

## 2. ขอบเขต

### สิ่งที่ทำ (In scope)

- ออกแบบระบบให้เก็บข้อมูลส่วนบุคคลน้อยที่สุดเท่าที่จำเป็น `[สมมติฐาน — ดู Q1]`
- นโยบายความเป็นส่วนตัว (Privacy Notice) และการแสดงต่อลูกค้าก่อนใช้งาน
- กลไกขอและบันทึกความยินยอม พร้อมช่องทางถอนความยินยอม `[สมมติฐาน — ดู Q4]`
- บันทึกรายการกิจกรรมการประมวลผลข้อมูล (ROPA)
- การเก็บข้อมูลจราจรทางคอมพิวเตอร์อย่างน้อย 90 วัน `[สมมติฐาน — ดู Q2]`
- มาตรการความมั่นคงปลอดภัยขั้นต่ำ — เข้ารหัสข้อมูล ควบคุมสิทธิ์เข้าถึง และบันทึกการเข้าถึง
- กระบวนการรองรับการใช้สิทธิของเจ้าของข้อมูล
- กระบวนการแจ้งเหตุละเมิดข้อมูลส่วนบุคคล
- การลบหรือทำให้ข้อมูลไม่ระบุตัวตนเมื่อครบกำหนดเก็บ `[สมมติฐาน — ดู Q3]`

### สิ่งที่ไม่ทำ (Out of scope)

- การจดทะเบียนภาษีมูลค่าเพิ่มและใบกำกับภาษีอิเล็กทรอนิกส์ (e-Tax Invoice) `[สมมติฐาน — ดู Q2]`
- การขอรับรองมาตรฐาน ISO 27001 หรือมาตรฐานความปลอดภัยอื่น
- การแต่งตั้งเจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล (DPO) — ดู Q5
- ~~การโอนข้อมูลส่วนบุคคลไปต่างประเทศ~~ — **ข้อนี้ถูกยกออกจาก out of scope แล้ว**
  เมื่อตัดสินใจใช้ Google Analytics ในเอกสาร [[20260802-03-cookie-consent-analytics|20260802-03]]
  ซึ่งมีการส่งข้อมูลไปยัง Google ในต่างประเทศ ประเด็นนี้จึงย้ายไปอยู่ในขอบเขตของเอกสารนั้น (BL-017)
- คุกกี้ การวิเคราะห์การใช้งาน และความยินยอมที่เกี่ยวข้อง — แยกไปอยู่ใน [[20260802-03-cookie-consent-analytics|20260802-03]]
- ข้อกำหนดเฉพาะของกฎหมายต่างประเทศ เช่น GDPR
- การร่างเอกสารสัญญาทางกฎหมาย — เป็นงานของที่ปรึกษากฎหมาย ไม่ใช่ของทีมพัฒนา

## 3. ผู้ใช้ที่เกี่ยวข้อง

| กลุ่มผู้ใช้ | สิ่งที่ต้องการจากระบบ |
| --- | --- |
| ลูกค้า (เจ้าของข้อมูล) | รู้ว่าร้านเก็บข้อมูลอะไร เอาไปทำอะไร และใช้สิทธิของตนได้ |
| เจ้าของร้าน (ผู้ควบคุมข้อมูล) | มั่นใจว่าระบบไม่สร้างความเสี่ยงทางกฎหมาย และมีหลักฐานว่าปฏิบัติตาม |
| พนักงานร้าน | เข้าถึงข้อมูลได้เท่าที่จำเป็นต่อหน้าที่ ไม่เกินกว่านั้น |
| ผู้พัฒนาระบบ | มีข้อกำหนดชัดเจนว่าต้องเก็บอะไร เก็บนานเท่าไร และต้องบันทึกอะไรบ้าง |
| ที่ปรึกษากฎหมาย | มีเอกสารตั้งต้นที่ระบุการไหลของข้อมูลจริง เพื่อตรวจสอบได้ |

## 4. User stories

- **US-1** — ในฐานะลูกค้า ฉันต้องการรู้ก่อนสั่งว่าร้านเก็บข้อมูลอะไรของฉันบ้าง เพื่อตัดสินใจได้ว่าจะใช้บริการหรือไม่
- **US-2** — ในฐานะลูกค้า ฉันต้องการขอดูและขอลบข้อมูลของตนเองได้ เพื่อใช้สิทธิตามกฎหมาย
- **US-3** — ในฐานะลูกค้า ฉันต้องการถอนความยินยอมได้ตลอดเวลา และถอนได้ง่ายเท่ากับตอนให้
- **US-4** — ในฐานะเจ้าของร้าน ฉันต้องการมีหลักฐานว่าลูกค้าให้ความยินยอมเมื่อใด เพื่อใช้ยืนยันเมื่อถูกตรวจสอบ
- **US-5** — ในฐานะเจ้าของร้าน ฉันต้องการให้ระบบลบข้อมูลเก่าอัตโนมัติ เพื่อไม่ต้องเก็บข้อมูลเกินความจำเป็น
- **US-6** — ในฐานะผู้ดูแลระบบ ฉันต้องการทราบทันทีเมื่อมีการเข้าถึงข้อมูลผิดปกติ เพื่อรับมือได้ทัน
- **US-7** — ในฐานะพนักงาน ฉันต้องการเห็นเฉพาะข้อมูลที่จำเป็นต่องาน เพื่อไม่ให้ตนเองมีความเสี่ยงโดยไม่จำเป็น

## 5. กฎทางธุรกิจ (Business rules)

- **BR-1** — เก็บข้อมูลส่วนบุคคลเท่าที่จำเป็นต่อวัตถุประสงค์เท่านั้น (data minimisation) ห้ามเก็บเผื่อไว้ใช้ทีหลัง
- **BR-2** — ทุกวัตถุประสงค์ของการเก็บข้อมูลต้องมีฐานทางกฎหมายรองรับ และต้องระบุไว้ใน ROPA
- **BR-3** — ต้องแสดงนโยบายความเป็นส่วนตัวก่อนเก็บข้อมูลครั้งแรกเสมอ ไม่ใช่หลังจากเก็บไปแล้ว
- **BR-4** — การถอนความยินยอมต้องทำได้ง่ายไม่น้อยกว่าตอนให้ความยินยอม
- **BR-5** — ข้อมูลจราจรทางคอมพิวเตอร์ต้องเก็บอย่างน้อย 90 วัน และต้องระบุตัวผู้ใช้บริการได้
  โดยแต่ละรายการต้องประกอบด้วยอย่างน้อย **IP address (แบบเต็ม) + วันเวลา + URL ที่เรียก +
  user agent + บัญชีผู้ใช้ (ถ้ามีการเข้าสู่ระบบ)**
- **BR-5.1** — ฐานทางกฎหมายของการเก็บข้อมูลจราจรคือ **หน้าที่ตามกฎหมาย ไม่ใช่ความยินยอม**
  จึงเก็บต่อไปได้แม้ลูกค้าปฏิเสธคุกกี้หรือถอนความยินยอม — ดู [[20260802-03-cookie-consent-analytics|20260802-03]]
- **BR-5.2** — ข้อมูลจราจรต้องแก้ไขย้อนหลังไม่ได้ และการเข้าถึงต้องถูกบันทึกไว้
- **BR-5.3** — ห้ามบันทึก request body หรือ response body ที่มีข้อมูลส่วนบุคคลลงในข้อมูลจราจร
  เพื่อไม่ให้ log กลายเป็นแหล่งข้อมูลส่วนบุคคลเพิ่มอีกแหล่ง
- **BR-5.4** — ต้องแจ้งเตือนผู้ดูแลระบบก่อนพื้นที่จัดเก็บ log เต็ม ห้ามลบ log ก่อนครบ 90 วันโดยอัตโนมัติ
- **BR-6** — รหัสผ่านต้องเก็บแบบ hash เท่านั้น ห้ามเก็บเป็นข้อความธรรมดาหรือเข้ารหัสแบบถอดกลับได้
- **BR-7** — ข้อมูลส่วนบุคคลต้องเข้ารหัสทั้งขณะส่ง (TLS) และขณะจัดเก็บ
- **BR-8** — พนักงานเข้าถึงข้อมูลได้ตามสิทธิขั้นต่ำที่จำเป็นต่อหน้าที่ (least privilege)
- **BR-9** — การเข้าถึงข้อมูลส่วนบุคคลโดยพนักงานต้องถูกบันทึกไว้ และ log ต้องแก้ไขย้อนหลังไม่ได้
- **BR-10** — เมื่อพบเหตุละเมิดข้อมูลส่วนบุคคล ต้องแจ้งสำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคลภายใน 72 ชั่วโมงนับแต่ทราบเหตุ เว้นแต่เข้าข้อยกเว้นตามกฎหมาย
- **BR-11** — ห้ามนำข้อมูลไปใช้นอกวัตถุประสงค์ที่แจ้งไว้ หากจะใช้เพิ่มต้องขอความยินยอมใหม่
- **BR-12** — ข้อมูลที่ครบกำหนดเก็บต้องถูกลบหรือทำให้ไม่ระบุตัวตนโดยอัตโนมัติ

## 6. เกณฑ์การยอมรับ (Acceptance criteria)

- [ ] **AC-1** — เมื่อลูกค้าเปิดหน้าสั่งอาหารครั้งแรก ต้องเห็นนโยบายความเป็นส่วนตัวก่อนกรอกหรือส่งข้อมูลใด ๆ
- [ ] **AC-2** — เมื่อลูกค้ากดยอมรับ ระบบต้องบันทึกวันเวลา เวอร์ชันของนโยบาย และวัตถุประสงค์ที่ยอมรับ
- [ ] **AC-3** — เมื่อลูกค้าไม่กดยอมรับ ระบบต้องไม่เก็บข้อมูลส่วนบุคคลใด ๆ ของลูกค้ารายนั้น
- [ ] **AC-4** — เมื่อค้นหาด้วยตัวระบุของลูกค้า ระบบต้องแสดงข้อมูลทั้งหมดที่เก็บไว้ของลูกค้ารายนั้นได้ภายในหน้าจอเดียว
- [ ] **AC-5** — เมื่อลูกค้าขอลบข้อมูล ระบบต้องลบหรือทำให้ไม่ระบุตัวตนได้ โดยยังคงข้อมูลยอดขายรวมไว้สำหรับบัญชี
- [ ] **AC-6** — เมื่อครบกำหนดระยะเวลาเก็บ ข้อมูลระบุตัวตนต้องถูกลบอัตโนมัติโดยไม่ต้องมีคนสั่ง
- [ ] **AC-7** — เมื่อตรวจสอบฐานข้อมูล ต้องไม่พบรหัสผ่านที่อ่านออกเป็นข้อความธรรมดา
- [ ] **AC-8** — เมื่อเรียกระบบผ่าน HTTP ต้องถูก redirect ไป HTTPS เสมอ
- [ ] **AC-9** — เมื่อพนักงานทั่วไปพยายามเข้าถึงข้อมูลส่วนบุคคลของลูกค้า ระบบต้องปฏิเสธและบันทึกความพยายามนั้น
- [ ] **AC-10** — เมื่อมีการเข้าถึงข้อมูลส่วนบุคคล ต้องมี log ระบุว่าใคร เข้าถึงอะไร เมื่อใด
- [ ] **AC-11** — เมื่อตรวจสอบย้อนหลัง 90 วัน ต้องมีข้อมูลจราจรทางคอมพิวเตอร์ครบถ้วนและระบุตัวผู้ใช้บริการได้
- [ ] **AC-11.1** — เมื่อเปิดรายการข้อมูลจราจรใด ๆ ต้องพบครบทั้ง 5 ส่วน — IP เต็ม วันเวลา URL user agent และบัญชีผู้ใช้
- [ ] **AC-11.2** — เมื่อลูกค้าปฏิเสธคุกกี้หรือถอนความยินยอม ข้อมูลจราจรต้องยังบันทึกต่อเนื่องไม่ขาดช่วง
- [ ] **AC-11.3** — เมื่อพยายามแก้ไขหรือลบรายการข้อมูลจราจรย้อนหลัง ระบบต้องปฏิเสธและบันทึกความพยายามนั้น
- [ ] **AC-11.4** — เมื่อค้นข้อมูลจราจร ต้องไม่พบ request body หรือ response body ที่มีข้อมูลส่วนบุคคล
- [ ] **AC-12** — เมื่อเปิดเอกสาร ROPA ต้องพบรายการข้อมูลทุกประเภทที่ระบบเก็บจริง ตรงกับฐานข้อมูลจริง

## 7. กรณีข้อผิดพลาดและกรณีขอบ

| กรณี | พฤติกรรมที่คาดหวัง |
| --- | --- |
| ลูกค้าถอนความยินยอมระหว่างที่ออร์เดอร์ยังทำไม่เสร็จ | ทำออร์เดอร์ต่อจนจบตามฐานสัญญา แล้วจึงลบข้อมูลระบุตัวตน |
| ลูกค้าขอลบข้อมูลที่ยังต้องเก็บตามกฎหมายภาษี | ปฏิเสธเฉพาะส่วนนั้น พร้อมชี้แจงเหตุผลและฐานกฎหมาย ห้ามเงียบ |
| นโยบายความเป็นส่วนตัวถูกแก้ไข | ขอความยินยอมใหม่จากลูกค้าเดิม ห้ามถือว่าความยินยอมเดิมครอบคลุมของใหม่ |
| ลูกค้าเป็นผู้เยาว์ | ต้องพิจารณาเรื่องความยินยอมของผู้ปกครอง — ยังไม่มีข้อสรุป ดู Q6 |
| ข้อมูลรั่วไหลนอกเวลาทำการ | ต้องมีผู้รับผิดชอบและช่องทางติดต่อที่ใช้ได้ตลอด เพราะกรอบเวลา 72 ชั่วโมงเดินตลอด |
| พนักงานลาออก | ต้องปิดสิทธิ์เข้าถึงทันทีในวันสุดท้าย และตรวจสอบ log ย้อนหลังได้ |
| ผู้ให้บริการภายนอกทำข้อมูลรั่ว | ต้องมีสัญญาการประมวลผลข้อมูล (DPA) กำหนดหน้าที่แจ้งเหตุไว้ล่วงหน้า |
| ลูกค้าอ้างว่าไม่เคยให้ความยินยอม | ต้องแสดงหลักฐานการยอมรับพร้อมวันเวลาและเวอร์ชันนโยบายได้ |

## 8. คำถามที่ยังค้าง

รายการนี้ต้องว่างก่อนเปลี่ยน `status` เป็น `ใช้งาน`

- [ ] **Q1 — ระบบจะเก็บข้อมูลส่วนบุคคลระดับไหน?** ปัจจุบันสมมติว่าไม่เก็บข้อมูลระบุตัวตนเลย
      (ผูกออร์เดอร์กับหมายเลขโต๊ะ) ทางเลือกอื่นคือเก็บชื่อ/เบอร์โทรเพื่อเรียกคิว หรือเก็บเต็มรูปแบบเพื่อทำสมาชิก
      **ผลกระทบ:** ถ้าไม่เก็บเลย งานส่วนใหญ่ในเอกสารนี้จะเบาลงมาก ถ้าเก็บเต็มรูปแบบจะเพิ่มขึ้นหลายเท่า
- [ ] **Q2 — ครอบคลุมกฎหมายฉบับใดบ้าง?** ปัจจุบันสมมติว่า PDPA + พ.ร.บ. คอมพิวเตอร์
      ทางเลือกอื่นคือ PDPA อย่างเดียว หรือเพิ่มเรื่องภาษีและ e-Tax Invoice
      **ผลกระทบ:** กระทบ BL-009 โดยตรง และเชื่อมกับคำถาม Q6 ของเอกสาร `20260802-01`
- [ ] **Q3 — เก็บข้อมูลออร์เดอร์นานเท่าไร?** ปัจจุบันสมมติว่า 1 ปี แล้วลบส่วนที่ระบุตัวตน
      ทางเลือกอื่นคือ 5 ปีตามอายุความบัญชี หรือ 90 วัน
      **ผลกระทบ:** กระทบ BR-12, AC-6 และ BL-013 — ต้องให้ฝ่ายบัญชียืนยัน
- [ ] **Q4 — ขอความยินยอมอย่างไร?** ปัจจุบันสมมติว่าแสดงนโยบายพร้อมปุ่มยอมรับก่อนสั่งครั้งแรก
      ทางเลือกอื่นคือแสดงลิงก์เฉย ๆ หรือแยกความยินยอมรายวัตถุประสงค์
      **ผลกระทบ:** กระทบ BR-3, BR-4, AC-1 ถึง AC-3 และ BL-007
- [ ] **Q5 — ต้องแต่งตั้ง DPO หรือไม่?** ยังไม่ได้ถาม ขึ้นกับขนาดและลักษณะการประมวลผลข้อมูล
      เป็นคำถามที่ต้องให้ที่ปรึกษากฎหมายชี้ขาด ไม่ใช่ทีมพัฒนา
- [ ] **Q6 — รองรับลูกค้าที่เป็นผู้เยาว์อย่างไร?** ยังไม่ได้ถาม
      ร้านกาแฟมีลูกค้าเด็กได้ตามปกติ หากเก็บข้อมูลระบุตัวตนจะมีประเด็นความยินยอมของผู้ปกครอง
      หากตอบ Q1 ว่าไม่เก็บข้อมูลระบุตัวตน คำถามนี้จะหมดไปเอง
- [ ] **Q7 — ใครเป็นผู้รับผิดชอบเมื่อเกิดเหตุละเมิดข้อมูล?** ยังไม่ได้ถาม
      ต้องมีชื่อผู้รับผิดชอบและช่องทางติดต่อจริง เพราะกรอบเวลา 72 ชั่วโมงเริ่มนับทันทีที่ทราบเหตุ
- [ ] **Q8 — ที่ปรึกษากฎหมายตรวจเอกสารนี้แล้วหรือยัง?** ยังไม่ได้ตรวจ
      **ห้ามเปลี่ยนสถานะเป็น `ใช้งาน` ก่อนข้อนี้ผ่าน**
